# The model ladder

Every task has a tier, and the ladder in `project.json` says which harness, model and effort runs each tier and each other job. `tower-crane ladder show` prints it and where each rung comes from; `docs/state.md` has the full shape and the precedence (project, then the user file `~/.config/tower-crane/config.json`, then built-in).

| Rung | Does | Good fit |
|---|---|---|
| `orchestrator` | plans, writes briefs, dispatches, runs gates, merges | the strongest model you have, in the harness you talk to |
| `easy` | `S` tasks by default: mechanical, local changes | a fast, cheap coding model |
| `medium` | `M` tasks by default | a strong coding model |
| `hard` | `L` tasks by default: cross-cutting or risky changes | the strongest coding model |
| `research` | tasks of kind `research` by default: open questions, measurements | the strongest model at high effort |
| `review` | fallback for clean-context review | used when no tier rung at the needed level can run |
| `small` | mechanical checks, such as confirming lines the cleanup tool flagged | a small fast model |

`task add` and `plan import` pick a tier from kind and size (`research` for kind `research`, else `S` easy, `M` medium, `L` hard); `--tier` overrides it, and only `--tier` changes it later.

```bash
tower-crane ladder harness codex                                  # every rung without its own harness
tower-crane ladder set easy     --profile luna --effort medium
tower-crane ladder set hard     --harness claude --model opus --effort high
tower-crane ladder set review   --profile sol --effort high
tower-crane ladder save-user                                      # make this ladder the default for new projects
tower-crane task update T3 --tier hard
```

A primary rung is `{ "harness", "model", "profile", "provider", "effort", "args", "command", "supervision" }`, every field optional; a rung without `harness` runs on the default harness. `ladder set` changes only the fields it names and `--clear FIELD` removes one. A write that would leave a rung unable to run (a codex profile on pi, a missing model) is refused. The Settings view of `tower-crane serve` edits the same ladder and each task's tier. [CLI: agents and worktrees](cli.md#agents-and-worktrees) lists the command and effort values each harness takes.

`tower-crane ladder set hard --supervision '{"retries":5,"backoff_ms":30000,"max_backoff_ms":600000,"stall_ms":300000,"progress_paths":["lib","test"]}'` sets retry and progress checks for that rung. `--clear supervision` restores the defaults. Reruns keep the resolved route. Codex and command adapters resume their session; Claude starts fresh with the brief and an interruption note. [State: supervision](state.md#projectjson) records the default values and their reasons.

Fallbacks are personal settings. In `~/.config/tower-crane/config.json` (or `TOWER_CRANE_CONFIG`), set `ladder.easy.fallbacks` to `[{"profile":"sol","effort":"high"},{"harness":"claude","model":"opus","effort":"medium"}]`. They apply to the easy rung in every project, even when the project defines its own primary. A user rung may contain only fallbacks. Project fallbacks and `ladder set --fallbacks` are refused. `ladder show` prints their user-file source and marks routes with unavailable harnesses, profiles or model settings; the supervisor skips these routes. The next route runs after an outage exhausts the current route's retries, or immediately after a structured harness policy refusal. Each fallback inherits the resolved harness and supervision unless it overrides them. Research Claude fallbacks also inherit the primary `web_mcp` unless they specify their own web server; other harnesses do not inherit it. An inherited or explicit web MCP cannot combine with `mcp`. Other fields are independent. Every switch starts a fresh session with the original brief, keeps the claim and worktree, resets the retry budget, emits `spawn-fallback` for the orchestrator, and attributes spend to the route that ran. Remove the field or set `[]` in the user file to disable it. No fallback is enabled by default.

## How each harness dispatches

A rung on claude, codex or opencode always runs through `tower-crane spawn`, including when the orchestrator runs on that harness: only a spawned agent gets its own environment ([Agent files and homes](#agent-files-and-homes)). A native subagent runs inside the orchestrator's session and shares its memory files, settings, hooks and MCP servers; no harness lets it have its own. A rung on agy or pi, which spawn does not isolate yet, may run as a native subagent when its harness is the orchestrator's.

- **Native** (agy and pi rungs only). Choose a unique name per attempt, claim workers with that name and a lease sized to the task, and pass the name, task, absolute worktree and state paths, skill path and brief. Every tower-crane call passes `--agent <name>` and, without `TOWER_CRANE_STATE`, `--state <dir>`. Workers use absolute paths under their worktree.
- **Spawned.** `tower-crane spawn --task <id>` runs the rung of the task's tier; `tower-crane spawn --role review --task <id>` selects a reviewer rung by task tier, diff risk and measured median review cost, with the review rung as fallback. Review dispatch requires passing software gates. Do not pre-claim. It starts the selected CLI in the task's worktree with `TOWER_CRANE_STATE`, `TOWER_CRANE_TASK` and `TOWER_CRANE_AGENT` set; a worker claims with that generated identity (`worker-T1-1`, `reviewer-T1-1`). pi loads the matching skill with `--skill`, codex finds it linked in its home, and claude gets its path in the home's instructions. Workers receive the brief. Reviewers receive the submitted diff, acceptance, gate results and only the brief's `## Reviewer` section, and use those results unless a focused probe is needed.
- **Custom command.** A rung with `"harness": "command"` and a `command` array runs any CLI; `{prompt}`, `{brief}`, `{task}` and `{cwd}` are substituted.

`tower-crane spawn --dry-run` prints the command without running it.

## Agent files and homes

Every agent runs under the agent file of its job in `agents/`: `tower-crane-worker.md` (`easy`, `medium`, `hard`), `tower-crane-researcher.md` (`research`), `tower-crane-reviewer.md` (`review`), `tower-crane-small.md` (`small`) and `tower-crane-orchestrator.md` (`orchestrator`). Each one lists, in its frontmatter:

| Key | Says |
|---|---|
| `tools`, `disallowedTools` | claude tools allowed and denied; denied commands as `Bash(<prefix>:*)` |
| `mcpServers` | always empty in the agent file: spawn adds explicit rung opt-ins and the user kit for browser tasks |
| `skills` | the tower-crane skill the job follows |
| `web` | whether it may browse or search |
| `gitPush` | `branch` (no force push) or `none` |
| `ghWrite` | the `gh` writes it may run; every other `gh` write is denied |
| `worktree` | `write` or `read`: whether its commands may change the worktree |
| `sandbox` | whether its commands run in the harness sandbox (claude's or codex's) |
| `writeOutside` | what its commands may write outside the worktree: `state` (the tower-crane state directory, for the unsandboxed orchestrator only; a sandboxed role changes state through the [state broker](#state-broker)), `git` (the repository's git directory and the worktree's admin directory inside it, named on its own because codex keeps a workspace's git directory read-only unless a rule names it, so a worker can fetch, add, commit and push), `cache` (a cache of the agent's own, `tower-crane/agents/<state hash>/<agent>` under `XDG_CACHE_HOME` or `~/.cache` (`%LOCALAPPDATA%` on Windows), for scratch, test temp files and tool caches; `XDG_CACHE_HOME`, `GOCACHE`, `GOMODCACHE` and `npm_config_cache` point into it, and it is removed with the agent's home. The cache root stays read-only: installed tools, gate commands and spawn receipts live there), and for the orchestrator `homes` and `worktrees` |
| `codexDisable` | codex features it does not get |

| Role | Tools | Web | git push | gh writes | Worktree | Writes outside it |
|---|---|---|---|---|---|---|
| worker | Bash, Read, Edit, Write, Grep, Glob, Skill | no | its branch, no force | `pr create`, `pr edit` | write | git, cache |
| reviewer | Bash, Read, Grep, Glob, Skill | no | no | `pr comment` | read | cache |
| small | Bash, Read, Grep, Glob | no | no | none | read | none |
| orchestrator | all but NotebookEdit | yes | branches, no force | reads plus `pr`, `issue`, `release`, `repo` (not `repo delete`), `api`, `workflow`, `label`, `gist` | write | unsandboxed: it starts the other agents, whose sandboxes do not nest in its own |

**Native agents cannot have an environment of their own.** A native subagent runs inside the session that starts it, so that session's memory files, settings, hooks and MCP servers reach it, whatever its agent file says. Claude Code still reads these files as plugin agent frontmatter (`tools` is the allowlist, `disallowedTools` the denials, `skills` is preloaded), but tower-crane never dispatches a claude, codex or opencode rung natively: those rungs always go through `tower-crane spawn` ([How each harness dispatches](#how-each-harness-dispatches)).

**Spawned claude, codex and opencode agents** get the file rendered to flags and a home of their own at `homes/<agent>/` in the state directory, built fresh, private (mode 700, files 600) and under the lock for every spawn: the harness config directory (`CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `OPENCODE_CONFIG_DIR`) and, inside it, `home/`, the agent's `HOME`. Nothing one agent writes there reaches the next, and a spawn removes the homes of agents whose process has exited. The user's memories, skills, plugins, hooks, MCP servers and approved-command rules never load, including what a harness finds under `HOME` (codex reads skills from `~/.agents/skills`). The agent's `HOME` links only `.gitconfig`, `.config/git`, `.config/gh`, `.aws` and `.ssh` from the user's.

**House rules** reach every spawn by path, never as copied text, so an edit applies to the next agent ([`lib/rules.js`](../lib/rules.js)). The chain starts with the user's global rules for the harness:

- Claude: `CLAUDE.md` and `rules/*.md` in the user's Claude config directory.
- Codex: `AGENTS.override.md` or `AGENTS.md` in the user's Codex home.
- OpenCode: `AGENTS.md` in the original user's `$OPENCODE_CONFIG_DIR`, or `$XDG_CONFIG_HOME/opencode` (default `~/.config/opencode`), falling back to the user's Claude `CLAUDE.md`.
- Pi: `AGENTS.md`, falling back to `CLAUDE.md`, in `$PI_CODING_AGENT_DIR` (default `~/.pi/agent`).
- Agy: `GEMINI.md`, `AGENTS.md` and `rules/*.md` in `~/.gemini` and `~/.gemini/config`, as named in its embedded customization docs and release notes.
- Command: the existing global files from all these locations. A custom command has no instruction discovery contract, so both its prompt and `{brief}` name the files to read. Spawn requires `{prompt}` or `{brief}` in the command argv and refuses before startup when neither is present.

The chain then includes `AGENTS.md`, `CLAUDE.md` and `CLAUDE.local.md` in every directory from the filesystem root down to the worktree (`.claude/CLAUDE.md` too, inside the repository), followed by their Claude `@path` imports. Codex prefers `AGENTS.override.md` over `AGENTS.md` in each directory. A Claude agent's home `CLAUDE.md` uses absolute import lines, quoting paths containing spaces or tabs and preserving literal whitespace; nested quoted or escaped imports are discovered too. `@~/` imports get another absolute import because Claude resolves `~` from the agent's isolated `HOME`. Only files reachable within Claude's five-hop limit, including the generated home's hop, are marked loaded; the prompt tells the agent to read the rest. Codex loads its selected worktree instruction file and reads the rest. OpenCode uses its isolated `HOME` and disables project instruction discovery. Every house-rule file is named in its prompt to read, using the original user's config location even in a nested dispatch; its receipt marks those files `read` and names the generated role file as `instructions_file`. Agy and Pi keep the user's `HOME` but still receive global and project files marked `read`, so the receipt makes no unverified loading claim. The prompt's `## House rules` lists each file as loaded or to read, and its `## Goal` states the project goal and the task's target and asks the agent to restate both in its first message. `spawn --dry-run` shows the chain with its size; a `startup` event records it for each started agent.

Measured on 2026-10-07 for this repository's T88 (bytes; tokens are about a quarter): before this chain, a claude worker loaded only its home `CLAUDE.md` (1.3 KB of role text): no repository `AGENTS.md`, no ancestor `~/projects/AGENTS.md`, and neither `~/.claude/CLAUDE.md` nor the `~/.config/agents/SHARED.md` it imports. A codex worker loaded its home `AGENTS.md` and the worktree's `AGENTS.md` (1,733), but not `~/.codex/AGENTS.md` (11,779) or `~/projects/AGENTS.md` (1,444). With the chain, the claude worker loads 14,273 bytes of rules (about 3,570 tokens) and the codex worker reads 13,223 more (about 3,300 tokens); the prompt grows by about 1,350 bytes (8,521 to 9,875 for claude, 9,830 for codex, with T88's rework brief).

`TOWER_CRANE_LIVE_CLAUDE=1` or `TOWER_CRANE_LIVE_CODEX=1 node --test test/live-rules.test.js` runs the real harness against rule files that each give a random house token: a user global file and its `@import` in a config directory of the test's own (linking the user's login, never writing the user's), an `AGENTS.md` above the repository and the repository's. The worker must name every token and restate the goal and target in its first message, and the `startup` event must list every file; it prints the startup size and the measured input tokens.

- **claude**: the config directory holds `CLAUDE.md` (the agent file's body, its skill's path and the house rules' `@path` imports), `settings.json` and `mcp.json`. `settings.json` carries only the provider settings from the user's `settings.json` (`CLAUDE_CODE_USE_*`, `AWS_REGION`, `AWS_PROFILE`, model and base URL names) the sandbox and Tower Crane message hooks. A credential helper the user sets (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`) is not copied, since the command may hold the credential: the home names `lib/auth-helper.js`, which reads and runs the user's command each time claude asks. `.credentials.json` is a link to the user's. Flags: `--setting-sources user` (so a repository's `.claude/settings.json` and `settings.local.json`, with their hooks and plugins, do not load), `--permission-mode acceptEdits`, `--tools` and `--allowedTools` from `tools`, `--disallowedTools`, `--strict-mcp-config --mcp-config <home>/mcp.json` and `--disable-slash-commands`. A credential kept only in the user's settings env reaches the agent only when spawn runs with it in its environment, as it does from a Claude Code session.
- **claude's sandbox**: every sandboxed role runs Bash in claude's own sandbox with `failIfUnavailable`, so a sandbox that cannot start stops the agent instead of running it unconfined, and `allowUnsandboxedCommands: false`. Writes: the worktree for a worker (and the repository's git directory, as claude allows for a linked worktree), never for reviewer and small, whose worktree is in `denyWrite`; plus the `writeOutside` directories: the agent's own cache for worker, reviewer and researcher test runs. The state directory, agent homes included, is in `denyWrite`: the [state broker](#state-broker) writes it. The agent homes and `brokers/` in the state directory are in `denyRead`; `allowRead` reopens only the dispatch's own home and its own `brokers/<agent>/`, so no agent reads another's broker token. `network.allowAllUnixSockets` is on, because the socket filter's seccomp helper needs a nested user namespace that hosts like this one refuse ("nested userns is capability-restricted"); in its place `denyRead` hides `/var/run/docker.sock`, `/run/docker.sock`, `/run/user/<uid>` (SSH agent, D-Bus, GPG) and the user's `~/.ssh` and `~/.aws`. Hiding a directory hides the sockets in it, so a sandboxed `connect()` there fails with `ENOENT` (`test/live-sandbox.test.js`, run with `TOWER_CRANE_LIVE_CLAUDE=1`); a socket in a directory not on that list stays reachable. The sandbox keeps a `.claude/.cc-writes/` directory in the worktree, which spawn adds to the repository's `info/exclude`. Network: all domains.
- **codex**: `config.toml`, and each `<profile>.config.toml`, are parsed and rebuilt from the user's files with only the model, provider and auth-store keys by name (never `model_instructions_file` or other instruction sources), providers in any TOML layout without any token, key, header, auth or env value, and the MCP servers the rung opted in to. It installs Tower Crane native message hooks and notify, grants trust to the generated hook commands with `-c bypass_hook_trust=true`, and adds the permission profile `tower-crane`: read anywhere, write the worktree only when `worktree` is `write`, write the `writeOutside` directories, temp and the agent's own `HOME`, read-only on the state directory, no access to other agent homes or to `brokers/` in the state directory except write on the agent's own `brokers/<agent>/` (codex mounts readable paths before it hides a directory and writable ones after, so a readable path under a hidden one is hidden too), network on. `AGENTS.md` holds the agent file's body (the prompt names the house rules); `rules/tower-crane.rules` forbids the denied command prefixes; `auth.json` and `.env` (where codex reads an AWS profile or Bedrock token) are links; the job's skill is linked under `skills/`; `sessions` links to `homes/.codex/<agent>/sessions`, which outlives the home so usage can be read after the agent exits. Flags: `-c default_permissions="tower-crane"` (`":danger-full-access"` for the orchestrator), `-c approval_policy="never"`, `-c web_search="live"` for research (or explicit `web_search` opt-in), `-c web_search="disabled"` otherwise, and `--disable` for each of `codexDisable`.
- **opencode**: `homes/<agent>/agents/gishra-<job>.md` is a generated primary agent selected with `--agent gishra-<job>` (research uses `gishra-researcher`). Its frontmatter and `opencode.json` contain native permissions: deny tools by default, allow the role's tools, restrict the skill tool to linked role skills, block web unless permitted or opted in, and limit file edits to the worktree and named writable directories. Read/edit patterns are relative to the worktree; external-directory patterns are absolute. Git push and gh command permissions follow the role; the same Git/gh shims check option order, force options and allowed writes. Only model and provider choices survive user JSON/JSONC config, with provider secrets removed. Selected provider and MCP objects merge recursively across layers; arrays and scalars replace the earlier value, so partial overrides retain connection fields and nested model options. MCP is empty unless the rung names servers; local `command` arrays and remote `url` values are kept without environment or headers. `auth.json` under the isolated XDG data directory links to the user's `~/.local/share/opencode/auth.json`, or its original XDG data location. Nested dispatches retain the original user's config and credential locations. `HOME`, `USERPROFILE` on Windows, and all four XDG directories belong to this dispatch. `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, inline config and `OPENCODE_PERMISSION` are replaced; project discovery and Claude compatibility are disabled. The only configured plugin is Tower Crane's generated message hook. Built-in authentication plugins remain enabled so the linked login works; inherited pure mode is cleared so the message hook loads. Opencode enforces tool permissions, not an OS shell sandbox: `TOWER_CRANE_SANDBOX=0`, and moving a confined worker, reviewer or small role to it is owner-required. Both its `sandbox` and `osSandbox` capabilities are false. Native edit denial does not constrain Bash writes or commands such as `git reset --hard`, so reviewer and small roles are not read-only at the shell level. The automatic browser kit remains Claude/Codex only; opencode uses explicit rung MCP opt-ins.
- **git and gh**: all spawned harnesses get `bin/` in the home first on `PATH`, holding `git` and `gh` shims (`lib/shim.js`) that allow a list and refuse the rest, aliases included, whatever the option order. git: git's own commands, wherever the sandbox lets them write (a reviewer's worktree is read-only, while the temp and cache dirs where test fixtures run `git init`, `git config` and `git commit` are not); a push to a repository on this machine, as test fixtures do, only in the plainest form `git push <dest> [refspec...]` with no option anywhere after `push` (git accepts abbreviated options, so any option voids the exception and the role and force rules apply), and only when every URL git would push to is a path or `file://` after git's own URL rewriting (`remote get-url --push --all` for a named remote, `ls-remote --get-url` for a URL or path) and no `pushInsteadOf` rule is set; and a push to another machine only on `gitPush: branch`, with no option but `-u`, `--set-upstream`, `-q`, `--quiet`, `-v`, `--verbose` and `--porcelain` spelled exactly (git accepts abbreviations, so any other could force, delete or mirror), no refspec that starts with `+` or `:`, and no `remote.*.mirror` key (whatever its value) or forcing `remote.*.push` in the configuration; a plain local push may force or delete, as fixtures do. Before the subcommand: `-C`, `-c` (only `user.name`, `user.email`, `init.defaultBranch`, `commit.gpgsign`, `tag.gpgsign`, `core.autocrlf`, `core.quotepath`, `advice.*` and `color.*`, since any other setting could rewrite a URL, add a push URL or define an alias), `--git-dir`, `--work-tree`, `--namespace`, `--no-pager`, `-P`, `--literal-pathspecs`, `--no-optional-locks`, `--bare`, `--no-replace-objects`. gh: read commands (`pr view`, `pr diff`, `pr checks`, `pr list`, `issue view` and the like) plus the role's `ghWrite`.
- agy, pi and `command` rungs get a private hook home, `TOWER_CRANE_HOOK` and the command shims while retaining their existing HOME and authentication setup. pi loads its generated extension through `--extension`. These rungs do not yet have permission renderers. Native dispatch does not install these adapters; automatic message delivery requires `spawn`. [CLI: event wakeups](cli.md#event-wakeups) lists live injection, stop handling and resume gaps.

**gh auth**: a gh login kept in the system keyring is out of a sandboxed agent's reach, since the sandbox hides the user's D-Bus socket. When the spawning environment has no `GH_TOKEN` or `GITHUB_TOKEN`, spawn asks `gh auth token` as the agent starts and hands the token to the agent process as `GH_TOKEN`. It is not written to files, argv, dry-run output or events. Agent commands can read `GH_TOKEN`, so a command that talks to GitHub without gh is not held to the gh allowlist. Harness output is persisted unredacted (the spawn log, and transcripts in the agent's home), so a token an agent prints is kept there.

Codex roles with `gitPush: branch` also get an explicit `git push` allow rule. This authorizes publishing without asking the orchestrator; the forbidden force prefixes and git shim still guard the push. Reviewer and small roles receive no push allow rule.

**Sandbox paths** are real paths: a state directory, git directory or cache reached through a symlink is named by its target in `allowWrite` and the codex permission profile, since that is what the sandbox mounts.

**Headless Chrome tests** use the existing temp-directory write access and browser-binary read access on both harnesses; they add no filesystem grants. Spawn sets `TOWER_CRANE_SANDBOX=1` only for sandboxed claude and codex roles, and `0` for unsandboxed roles and other harnesses, replacing any inherited value. `test/browser.js` gives each browser a temporary profile. Only inside an agent sandbox does it redirect browser `HOME`, config, cache and temp directories into that profile, so crashpad does not need writes under the agent's home. In an outer sandbox it adds `--disable-dev-shm-usage` to use that temp storage instead of writable `/dev/shm`, and `--no-sandbox`: Chrome's user/SUID sandbox cannot nest in the harness's bwrap sandbox, so the outer sandbox confines the browser instead. Host runs retain the original inherited environment, ignored stderr and flags, including the existing root `--no-sandbox` exception. The installed browser and its libraries remain read-only; the helper removes the profile on exit and reports browser stderr on sandboxed startup failure.

**Browser kit**: tasks with `kind: "design"` or `needs: ["browser"]` get the user's browser MCP servers on every Claude/Codex rung, including reviewer, small and orchestrator. Declare it with `task add/update --needs '["browser"]'`, or use kind `design`. The user file's `browser_kit` is a list of server names, default `["playwright"]`; `browser-kit set --servers '["playwright","visual"]' --agent owner` changes it, and `[]` disables automatic attachment. The kit is read at each dispatch, merges with explicit rung opt-ins, and follows the original user through isolated orchestrator homes. Other tasks get no automatic kit. Missing named definitions and unsupported harnesses omit kit servers and continue. Only explicit `needs: ["browser"]` refuses dispatch when no primary or fallback route can attach a configured kit server. An implicit design task still runs on pi, opencode, agy or command, including reviewer and small roles. Spawn output and `spawn`/`spawn fallback` events report `browser_kit: { requested, attached, omitted, warning }`; each omitted route explains why it runs without the kit.

Claude reads named definitions from the user's config directory `mcp.json`, falling back to `~/.claude.json`, and pre-approves `mcp__NAME`. Codex reads `[mcp_servers.NAME]` and sets the selected servers' default and per-tool approvals to `approve`, including profile overrides. Neither copies the kit's env or headers. Generated instructions name the approved servers. Configure the user's browser server and install its browser ahead of dispatch; Tower Crane does not install tools or guess server commands. The kit adds no filesystem grants: the existing read-only browser path and per-browser temp profile suffice for sandboxed command tests. MCP subprocesses follow the harness's MCP launch policy; the command sandbox applies to Bash/shell tools, so Tower Crane does not inject `--no-sandbox` into MCP server arguments.

Run `TOWER_CRANE_LIVE_BROWSER=1 node --test test/live-browser.test.js` from an unsandboxed Linux session with logged-in claude and codex CLIs, Chrome installed and the browser kit configured in both harnesses. The opt-in probe spawns one real sandboxed worker per harness on a design task. It requires MCP navigation to the board, a PNG screenshot and one board browser test to pass; a missing Chrome, skipped browser test or worker that omits an action fails. `TOWER_CRANE_LIVE_BROWSER_HARNESS=claude` or `codex` selects one harness, `TOWER_CRANE_LIVE_MODEL` selects the Claude model (`opus` by default), and `TOWER_CRANE_LIVE_PROFILE` selects the Codex profile (`sol` by default). `TOWER_CRANE_TEST_CHROME` names a browser outside `PATH`.

Every spawn removes the outer Node test runner's `NODE_TEST_*` variables before launching an agent, including retries and fallback routes; configured env values cannot restore them. This lets the worker's `node --test` run its own tests. The live probe rejects stderr, nonzero exits and empty test output, and prints the child receipt and agent log tails on failure.

The owner can extend those paths with project or rung `sandbox.write`, set literal variables with `env`, and load secrets at spawn through `env_file`. Project or rung `scope` properties launch the agent itself under a host systemd user scope; commands inherit its CPU and memory limits and receive `TOWER_CRANE_SCOPED=1`. Configured scopes require Linux, `systemd-run` and a working user manager. The command sandbox keeps the session bus inaccessible. Both harnesses enable TCP loopback sockets. See [state.md](state.md#ladder) for precedence, file quoting and the security limits, and [cli.md](cli.md#run) for commands.

Credentials are never copied: the home links to the user's file itself, resolved past any link, so a refreshed token is seen at once, nothing tower-crane writes holds one, and a spawn started inside another agent (with that agent's home as its `HOME` and config directory) links to the user's original files, never into the parent's home, so removing the parent breaks nothing. Each home records where the user's files are in `.tower-crane-origin.json` for that case. On Windows a file link falls back to a hard link when symlinks need developer mode.

A rung opts back in with `tools` and `mcp`: `tower-crane ladder set review --tools '["WebFetch"]' --mcp '["docs"]'`. The orchestrator or the owner changes a rung's harness, `args`, `tools` or `mcp`, as long as a worker, reviewer or small rung and its fallback routes stay on harnesses with OS command confinement declared in `lib/agents.js`, and args follow their allowed flags; moving one elsewhere, by `ladder set`, a fallback route or `ladder harness`, or args on an unsandboxed harness open a `ladder.reach` decision. `command` and the sandbox, environment and scope fields are owner-required, so the orchestrator's change opens a decision ([state.md: Authority](state.md#authority)). The orchestrator's `mcp` names only servers the owner's harness config already defines, and its `tools` only harness built-ins that keep the rung's sandbox; another tool, such as claude `Edit` on the review rung or codex `computer_use`, opens a `ladder.reach` decision. A worker asks the orchestrator. An opted-in claude tool joins `--tools` and leaves `--disallowedTools`; an opted-in codex feature is enabled, and `web_search` turns search back on. On an owner-selected opencode route, native tool names (`webfetch`, `websearch`) and their agent-file names (`WebFetch`, `WebSearch`) are normalized before authority classification and have the same operational opt-in behavior; its rung MCP names select `mcp.NAME` from the original user config. Both opt-ins appear in dry-run output. An opted-in MCP server is taken by name from the user's harness config with its command, args and URL but without its `env` or headers, so a secret it needs comes from the environment; claude pre-approves its tools (`mcp__<name>`). `spawn --dry-run` names both. A claude, codex or opencode rung's `args` may hold only these flags, each as its own argument: claude `--verbose`, `--max-turns N`, `--fallback-model M`, `--append-system-prompt TEXT`; codex `--skip-git-repo-check`, `--ephemeral`, `--color WHEN`, `--disable FEATURE`, and `-c KEY=VALUE` for the model, provider and auth-store keys. Opencode permits only `--title TEXT`; selecting another agent, attaching to another server or automatic approval through extra arguments is refused. Anything else is refused.

Limits. The orchestrator runs unsandboxed on both harnesses: it starts the other agents, which build sandboxes of their own that do not nest inside one. The shims see `git` and `gh` as found on `PATH`: a program called by its absolute path, or run from a script, is not checked. On macOS, claude keeps an OAuth login in the keychain under a name tied to the config directory, so a subscription login does not carry over to a home; API key, Bedrock and Vertex setups do.

## State broker

A sandboxed agent reads the state directory but cannot write its state: `project.json`, `tasks.json`, `decisions.json`, `events.jsonl`, the lock, the logs and other agents' homes are read-only or hidden in its sandbox. What its commands can still write there is its own: for codex its `HOME` (`homes/<agent>/home/`), its sessions (`homes/.codex/<agent>/`, which `spend --from-spawn` reads, so the usage collected from them is the agent's own report) and its `brokers/<agent>/`, which the broker never reads back; for claude nothing, though the harness process itself writes its config directory, `homes/<agent>/`. For a claude or codex agent whose file says `sandbox: true`, the spawn monitor, which runs outside the sandbox, listens for that agent alone for as long as it supervises it (`lib/broker.js`). It writes `broker.json` into the agent's private broker directory, `brokers/<agent>/` in the state directory (mode 700, the file mode 600), with the address and a random token made for that spawn, and starts the agent with `TOWER_CRANE_BROKER` naming that file. For a claude agent the address is a Unix socket, `broker.sock` in that directory, or, when that path is too long for a socket address, in a fresh private directory under the temp dir; claude's sandbox has no host loopback. Codex's sandbox refuses connecting to a Unix socket, so for a codex agent it is TCP on `127.0.0.1` at an ephemeral port (`host` and `port`), which any local process can reach; the token, readable only by that agent, is what admits a request. On Windows it is a named pipe. The broker serves the whole spawn, its personal fallback routes from the user file included: it starts when any route runs a sandboxed harness, listens on what each of those harnesses needs (both, for a rung that falls back from claude to codex or back, the agent trying the socket first), and every sandboxed route gets `TOWER_CRANE_BROKER`. `test/live-sandbox.test.js` checks both against the real harnesses, a forged write refused and a note recorded through the broker; run it from an unsandboxed user session with `TOWER_CRANE_LIVE_CLAUDE=1` or `TOWER_CRANE_LIVE_CODEX=1`. In the agent, a tower-crane command that only reads (`task show`, `task list`, `brief get`, `project show`, `ladder show`, `validate`, `ready`, `decisions`, `status`) runs as usual; any other command aimed at the broker's state directory goes to the broker, and one aimed at another state directory, such as a test fixture's, runs in the agent. The broker checks the token, refuses an `--agent` that is not the spawned agent's name, allows only the role's commands on the agent's own task (positional ID, `--task` and `--blocks`), and runs the command as a CLI process outside the sandbox in the task's worktree, as the spawned agent on the spawn's state directory, naming `--agent` and `--state` before the agent's own arguments so a `--` among them stays the agent's. Records it writes carry `"via": "broker"`; that is provenance, not proof, since any unsandboxed process can write the same. Roles and their commands: worker `claim`, `renew`, `release`, `submit`, `spend` (its own spawn only), `task note`, `msg` and `ask`; reviewer `evidence --type review`, `task note` and `msg`; small `task note`; and every role `hook`, for the [message hooks](#agent-files-and-homes), with its own `homes/<agent>/hook.json` binding only. `worktree` runs in the agent, as a read: it prints the worktree spawn made. The broker runs outside the sandbox, so it never executes anything the agent controls: no `check` (the project's tests and cleanup are the agent's code, and `--cmd` is its shell) and no git, whose repository config and commits the worker writes and which can run commands they name (merge drivers, `core.fsmonitor`). A command it runs finds no repository, and does not render the sketch, whose gate report reads the repository; the next write outside the broker renders it. A resubmit that checks the task's PR runs `gh pr view -R` with the project's `repo` and no repository for git to read, and is refused when `repo` is unset. A worker runs its tests in its own sandbox; the gates that run code (`check`, `merge`) are the orchestrator's. A command that reads stdin (`-` as a value) sends it with the request. The orchestrator is unsandboxed and writes the state itself. The broker closes when the agent exits: it removes the broker directory, drops open connections and kills any command it is still running together with every process under it, so nothing it runs writes after the spawn ends; the token is no longer accepted anywhere. Agents on other harnesses are not sandboxed and write the state as before.

## Research network tools

The research rung renders `tower-crane-researcher.md`, with the same file permissions, git/gh shims, writable paths and sandbox as a worker. It permits web tools and requires actual network research with at least `research.min_sources` distinct cited pages (default 10). Its generated identity remains `worker-<id>-<n>` and it follows the work skill. Claude permits native `WebSearch` and `WebFetch`; its sandbox allows outbound domains `*` while preserving worker file confinement. Codex explicitly uses `-c web_search="live"`; `codex --help` on 2026-10-07 describes `--search` as enabling the native live Responses `web_search` tool. HTTP fetching through Bash retains the same command sandbox.

Claude providers such as Bedrock may lack native web tools. Configure just the web server in the project or user ladder:

```sh
tower-crane ladder set research --web-mcp '{"name":"harness-web","command":"node","args":["/absolute/path/to/harness-web/server.mjs"]}' --agent owner
```

The user defaults use the same `ladder.research.web_mcp` object. Its allowed fields are only `name`, `command` and `args`; secrets belong in the inherited process environment or the owner-configured environment file. Do not copy `env` from `~/.claude.json`. Use absolute script paths for portability across isolated homes; a bare executable command resolves on PATH. Claude loads only this server through `--strict-mcp-config --mcp-config <home>/mcp.json` and approves only `mcp__<name>__websearch` and `mcp__<name>__webfetch`. Native web tools are omitted in this mode. `web_mcp` applies only to research on Claude and cannot combine with `mcp`. Other roles retain their existing tool defaults and explicit owner opt-ins.

OpenCode, agy, pi and command receive researcher instructions, but have no Tower Crane sandbox or web-tool renderer. Configure their search/fetch tools and equivalent file/git confinement in their harness or command wrapper before dispatch; Tower Crane does not enforce those harness permissions. Tasks of kind research on every tier still require the same sources gate and claim-to-citation review. Commit the structured deliverable described in [state.md](state.md#research-sources).

## Review selection

`tower-crane accept` refuses review evidence recorded by the agent that submitted the task. Review dispatch gives the reviewer a clean context, so its model may match the builder. Selection starts at the task tier, raises for a broad or risky diff, and promotes to a stronger tier when T31 review spend shows its median cost is no higher. Unknown usage leaves the complexity choice intact. The `review` rung is used when no tier rung at the needed level can run. `tower-crane validate` warns only when no reviewer rung can run.

Only an explicitly identified owner can set `project set --review-policy JSON`. Its prices use canonical model identities shared by rungs and spend entries: `sol` resolves to `openai.gpt-6.1-sol`, `luna` to `openai.gpt-6-luna`, and `opus` to `claude-opus-5-5`.
