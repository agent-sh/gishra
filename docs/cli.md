# CLI

Command tables are generated from `COMMANDS` in `bin/tower-crane.js` with `npm run docs:generate`. CI rejects drift; keep further contract details outside the generated blocks.

`tower-crane <command> [args]`. Every command accepts `--state DIR`, `--agent NAME`, `--json` (machine output on stdout: the task, decision, project or list the command touched) and `--help`. Exit status: 0 done, 1 refused (with the reason on stderr), 2 usage error or wait timeout, 3 lock not acquired within 10 s. `validate` and a failing gate print their report on stdout and exit 1; `spawn --wait` exits with the agent's code. `wait` always prints one compact JSON line, including with `--json`. If a reader closes stdout or stderr, the CLI treats the resulting `EPIPE` as a quiet close, finishes the command and any state write, lets the other output stream drain, then exits with that command's status.

Agent identity comes from `--agent NAME`, then `TOWER_CRANE_AGENT`. With neither, `owner` is used only when stdin and stdout are both TTYs and `TOWER_CRANE_TASK` is unset. Otherwise the command exits 2 with `no agent: pass --agent NAME or set TOWER_CRANE_AGENT` and writes nothing. An empty or whitespace-only identity exits 2 with the same message. Help needs no agent.

When `TOWER_CRANE_TASK` is set, resolving either identity source to `owner` is refused. The owner acts from an interactive terminal; a task process cannot use owner identity.

Guarded settings and commands are operational or owner-required, per the one table in [state.md: Authority](state.md#authority). The orchestrator or the owner makes operational changes; the orchestrator's owner-required change opens a decision for the owner (exit 1, naming the decision) and changes nothing. The owner is the resolved name `owner`, supplied explicitly by `--agent owner` or `TOWER_CRANE_AGENT=owner`; the terminal fallback never grants authority. Workers and reviewers ask the orchestrator for operational changes with `tower-crane msg --to orchestrator` or a task note. Any agent may release a spawned claim verified exited under the lock.

In a sandboxed claude or codex agent (`TOWER_CRANE_BROKER` set by its spawn), commands that only read, and `worktree` for the worktree spawn made, run as usual, and every other command on the spawn's state directory is sent to the [state broker](ladder.md#state-broker), which runs it as the spawned agent if its role allows it on its own task, and prints its output and exits with its code. A refused command exits 1 and writes nothing. The broker refuses `check`: it runs outside the sandbox and never runs the agent's code, so a worker runs its tests directly and the orchestrator runs the gates.

Writes take the lock, re-read the files, validate, write atomically and append to `events.jsonl`. The Git/gh runner refuses commands inside mutation transactions. Rendering follows after the mutation releases its lock and reads current state under its own lock. A refused command writes nothing.

`project set --tests-paths '["src/test/**","**/*Test.java"]'` replaces `tests.paths` with a non-empty JSON array of non-blank strings. `--tests-paths null` removes the field and restores the default test layouts; `[]` is invalid.

`project set --tests-keep '["Makefile","tools/**/*.gradle"]'` sets `tests.keep`, an array of extra build file globs to keep at the submitted sha during the tests gate's revert run. These extend the default declarative manifests and lockfiles listed in state.md. Executable build files such as `Makefile`, `setup.py`, Gradle scripts and bundler configs require this explicit setting. Use narrow globs: any matched non-test code stays unreverted. `--tests-keep '[]'` or `--tests-keep null` restores the default keep set; neither disables it. Test paths take priority and are not listed as kept build files.

`project set --tests-mode prove --tests-by-kind '{"code":"run-only"}'` sets the tests policy for a project with inline tests. Modes are `prove` (default, pass at head and fail after reverting other changes), `run-only` (pass at head once), and `none` (skip the suite and verify the submitted commit). Kind overrides replace the whole map and take priority over the project mode; keys must be `code`, `docs`, `research`, `design` or `ops`. Only code tasks require tests evidence for acceptance; other kinds already use independent review, and their modes apply to explicit tests checks. Use `run-only` for Rust inline `#[cfg(test)]` modules in production source files. `--tests-mode null`, `--tests-by-kind null` and `--tests-expensive null` remove their respective fields. `{}` clears kind overrides and false restores normal proof. These flags also work with `init` and preserve other tests settings.

All five tests settings flags (`--tests-mode`, `--tests-by-kind`, `--tests-expensive`, `--tests-paths`, `--tests-keep`) are operational on `init` and `project set`, including clearing or setting the same value: the orchestrator or the owner. A refused call writes no state, including any other settings in that call. Workers ask the orchestrator through `tower-crane msg --to orchestrator` or a task note.

Gate commands come from `project.json gates`. The orchestrator or the owner pins them with `project set --tests-cmd "npm test" --clean-cmd "node /path/to/deslop/scripts/detect.js"`. `init` accepts the same settings. The cleanup value is a command prefix; the gate appends its checkout directory, `--base=SHA` and `--json`. `--tests-cmd null`, `--clean-cmd null` and `--tests-proof-cmd null` clear the respective pins. Non-blank strings without NUL bytes are required. An unpinned project does not block: when the orchestrator or the owner runs `check tests`, `check clean` or `accept` with a needed pin missing, the engine first pins `npm test` (when `package.json` has a real test script) and the configured cleanup tool (`TOWER_CRANE_CLEAN_CMD`, `deslop` on PATH or the deslop plugin script), logs a `gates pin` event and lists it in `status`. Otherwise missing pins refuse execution, except tests mode `none`, which needs no test command; workers and reviewers pin nothing.

For expensive suites in `prove` mode, the orchestrator or the owner sets `project set --tests-expensive true --tests-proof-cmd "node --test {tests}"`, then callers run `check tests ID`. The full suite runs once at head. `{tests}` is replaced with the shell-quoted added or changed test paths, and that scoped command must pass at head and fail with non-test files reverted. A pinned scoped template containing `{tests}` is required before the full suite runs when there are changed tests and revertible files. Test-only and kept-build-file-only changes retain the normal head-only exception. The orchestrator or the owner chooses the scoped runner and the reviewer checks that it selects those files. `run-only` and `none` are unaffected by the expensive setting.

Optional `--cmd` and `--proof-cmd` flags must match the corresponding pin after trimming surrounding whitespace; they cannot select another command, including when passed to `accept` or in tests mode `none`. A non-blank `TOWER_CRANE_CLEAN_CMD` must match `gates.clean_cmd` too. Only the orchestrator or the owner can set or clear pins, including setting the current value. A changed pin makes the affected gate's previous receipts stale; rerun that gate before acceptance or merge.

`project set --ci-ignore-apps '["claude","cursor"]'` replaces `ci.ignore_apps` with a JSON array of non-blank strings naming GitHub apps. `--ci-ignore-apps '[]'` stores an empty ignore list; `--ci-ignore-apps null` removes the field. Both make the CI gate check every app again.

`project set --ci-required '["test (","lint"]'` sets `ci.required`, an array of required check-run names or literal, case-sensitive prefixes. Each entry must match at least one run outside ignored apps at the submitted sha, and every matching run must be completed with conclusion `success`. Skipped, neutral and capped runs cannot satisfy required jobs. A prefix such as `"test ("` covers jobs that ran but cannot detect an absent matrix member; list each full job name to require every member. Tower Crane's own project requires `["test (ubuntu-latest, node 26)","test (ubuntu-latest, node 24)","test (windows-latest, node 26, shard 1/3)","test (windows-latest, node 26, shard 2/3)","test (windows-latest, node 26, shard 3/3)"]`. `--ci-required '[]'` or `--ci-required null` clears this requirement. `init` accepts the same flag.

`project set --ci-capped-review '[{"app":"cursor","pattern":"usage limit"}]'` sets `ci.capped_review`: a failed check run of that GitHub app whose output title or summary matches the case-insensitive pattern is a nonblocking capped review. `[]` or `null` clears it.

Changing the effective `ci.required`, `ci.ignore_apps` or `ci.capped_review` policy makes a previous hosted CI pass stale. Acceptance and the merge recheck require `tower-crane check ci ID` again, even at the same submitted head.

All list settings trim leading and trailing whitespace from each entry. Setting a list replaces a non-object `tests` or `ci` section; clearing it removes that malformed section. Object sections keep their other fields. Text output from `project set` and `project show` prints these lists, with `default layouts` for absent test paths and `[]` when no extra build files, CI apps or required checks are configured. Test and CI gate hints name the corresponding `project set` flags.

`project set --ci-local '{"command":["python3","tools/check.py"],"timeout":120}'` configures local CI. `command` is a nonempty argv array with a nonblank executable and string arguments, passed verbatim without a shell. Empty arguments are allowed; NUL bytes are refused. `timeout` is required, in positive seconds, within Node's timer range of 2147483647 milliseconds. There is no default timeout. `--ci-local null` removes local CI and restores hosted checks. Other `ci` fields are preserved. `init` accepts the same setting; `project show` prints `ci.local: hosted` when it is absent. Every use of `init --ci-local` and `project set --ci-local`, including clearing or setting the current value, is operational: the orchestrator or the owner.

`project set --merge-keep-branch true` sets `merge.keep_branch` and omits `gh pr merge --delete-branch`. Use it for projects that retain worktrees holding task branches. It keeps branches even when no worktree holds them. `--merge-admin true` sets `merge.admin` and adds `gh pr merge --admin`, for repositories solely owned by the project owner per SHARED.md. Setting or clearing admin policy is owner-required; `--merge-keep-branch` is operational. Both settings also work with `init`, accept JSON true, false or null, and preserve other merge settings. False disables the option; null removes the field. Both default to false and appear in `project show`.

`ci.local.by_kind` optionally maps `code`, `docs`, `research`, `design` or `ops` to overrides. Each override has exactly one of `command` (replace the default argv) or `args` (append to the default argv), plus an optional `timeout` in seconds. An omitted timeout inherits `ci.local.timeout`. Empty `args` selects the default command as a distinct variant. Unknown kinds, unknown override fields and invalid argv or timeouts are refused without writing state.

```sh
tower-crane project set --ci-local '{"command":["python3","tools/check.py"],"timeout":120,"by_kind":{"code":{"args":["--native-extended"]},"ops":{"args":["--lab"],"timeout":300}}}'
tower-crane task update T1 --ci-local '{"args":["--s3"],"timeout":600}' --agent owner
tower-crane task update T1 --ci-local null --agent owner
```

`task update --ci-local` stores `ci_local` on the task; setting or clearing it is operational. Its shape is the same as a kind override. A task override takes precedence over the kind mapping and resolves against the project default command and timeout. Clearing it restores the kind mapping, or the default if that kind has no mapping. Overrides apply only while project local CI is configured; they do not select local CI on a hosted project. `task show` prints a stored override. Workers ask the orchestrator for a different tier through `msg --to orchestrator` or a task note.

`merge` defaults to `--method squash`, with the task title as the commit subject and its acceptance lines joined by newlines as the body. `--subject` and `--body` override these independently, preserving multiline text and an explicitly empty body. A subject must be non-blank. `--method merge` uses the same commit text options; `--method rebase` omits them and refuses explicit subject or body overrides. Every merge invocation uses GitHub's full head SHA with `--match-head-commit` after verifying it matches the accepted SHA. Branch deletion is requested unless `merge.keep_branch` is true. Only owner-set `merge.admin: true` adds GitHub's admin option for solely owned repositories. There is no one-off `merge --admin` flag; acceptance, review, CI and head checks still apply.

`project set --review-policy JSON --agent owner` replaces `review` with optional diff limits, risk paths and prices. Only an explicitly identified owner can set this policy or its prices. For example:

```sh
tower-crane project set --review-policy '{"small_lines":100,"small_files":5,"risk_paths":["auth/**"],"prices":{"openai.gpt-6-luna":{"input":0.10,"cache_write":0.125,"cache_read":0.01,"output":0.50},"openai.gpt-6.1-sol":{"input":2,"cache_write":2.50,"cache_read":0.10,"output":10},"claude-opus-5-5":{"input":4,"cache_write":5,"cache_read":0.20,"output":20}}}' --agent owner
```

Rates are dollars per million tokens; use the actual provider model IDs and rates. Profile aliases `sol`, `luna` and `opus` normalize to `openai.gpt-6.1-sol`, `openai.gpt-6-luna` and `claude-opus-5-5`. The example uses Bedrock global rates with five-minute cache writes. Selection starts at the task tier, raises easy to medium for diffs over 100 lines or 5 files by default, and raises to hard for matching risk globs or binary changes. It promotes to a stronger tier when T31's recorded review spend has a median priced cost no higher. Each failed independent review at the current head climbs one tier. The `review` rung is the fallback when no tier rung can run. The reviewer may use the builder's model because its context is clean. Missing complete usage prevents cost promotion. `--review-policy null` restores diff defaults without prices. See state.md for the pricing limits of older inclusive telemetry.

Briefs can use `## Shared`, `## Worker` and `## Reviewer` level-two headings. Matching is case-insensitive, and headings inside fenced code blocks are ordinary text. Content before the first role heading is shared; each section runs to the next role heading. `## Rework notes` also starts a shared section, so corrections appended by `rework` stay visible to role-filtered brief readers. `brief get ID` infers worker or reviewer from the `--agent` or `TOWER_CRANE_AGENT` name. Use `--role worker` or `--role reviewer` to select explicitly. Owner and orchestrator identities see the full brief by default.

`init --review-policy JSON` accepts the same operational setting.

The list settings also work with `init`. Omitted options leave their fields unchanged. Removing a field keeps other settings in its object section and removes the section itself only when empty. Invalid JSON, a value other than an array or `null`, or a blank or non-string array entry exits 2 and writes no state or event, including when combined with valid settings.

## Run

Dependent tasks can start while a single dependency chain is submitted or accepted but unmerged. `worktree` and `spawn` check the GitHub stacks endpoint, verify the dependency PR's current head and repository, fetch its branch, and create the upper branch at that head. The worker prompt names the dependency branch as the PR base. `ready` and `claim` allow submitted dependencies when they form one chain with a PR, branch and sha; dispatch still verifies availability. Independent dependency chains and forks wait for the ordinary accepted-dependency flow. A worktree made before its dependency was submitted is revalidated at dispatch: a clean branch with no commits of its own moves onto the dependency head, and one holding its own work is refused until the worktree is removed or the dependency merges. Two siblings prepared at once on the same dependency cannot both record it as their stack parent; the second dispatch is refused under the lock and waits as a fork.

The dispatch supervisor links submitted PRs with `gh stack link <lower-pr> <upper-pr>` in bottom-to-top order. Native dispatches use `stack link ID` after recording the PR with `submit`. Linking verifies every member's submitted head, PR base and same-repository origin. Auto-merge must be disabled. Workers retain their existing gh permissions; linking and synchronization run under the dispatcher's policy.

Stack operations that contact GitHub and change task metadata, including dispatch and merge, share one snapshot of the project, members and member events, execute GitHub commands without the state lock, then compare against freshly read state before applying. Linking, retirement and unstacking preserve concurrent claims and refuse changed member or project inputs. A refusal can follow a successful remote operation, so inspect the PRs and branches before retrying. Automatic linking follows the collector's state write.

When stacks become available again, a successful `stack link ID` clears ordinary-merge fallback markers for that chain and restores the stack merge guard.

If every lower task merges before an unlinked dependent submits its PR, `stack link` retargets that PR to the project base and clears its local stack. The submitted head is preserved and the ordinary merge gate applies. Supervisors perform the same transition when observing a submission.

`merge ID` uses `gh stack merge <pr> --yes --squash` for linked stacks. It verifies remote stack membership and refuses unknown lower PRs, checks every task below the target is accepted with passing gates, and re-reads every PR head immediately before the merge, then refuses if the project settings, stack members or their events changed since the merge started. Merge evidence for PRs that landed is always recorded; fallback markers and retargeted bases apply only when that stack state is unchanged. Stack merge has no `--match-head-commit`; a push after the checks remains a race. Confirmation checks every merged PR against its accepted sha and records separate merge evidence for each task that actually landed. A queued stack gets no successful merge evidence until GitHub confirms it merged.

After a lower merge, or when a later `worktree` or `spawn` observes main or a dependency moving, Tower Crane refreshes upper worktrees through `gh stack sync`. A dependent prepared before its PR is linked is revalidated at each `worktree` and `spawn`: when its dependency was resubmitted, a branch with no work of its own moves onto the new dependency head, and a branch with its own commits is refused until it contains that head (merge it in, or remove the worktree and branch). Every worktree in that stack must be idle and clean; otherwise refresh is deferred and an event names the blocker. Unknown remote PRs must be recorded before sync. Sync snapshots the project, stack members and their events under a short state lock, runs gh and Git unlocked, then re-takes the lock to compare and apply. Changes to the project or affected tasks refuse application and preserve current claims; unrelated task writes are retained. Git may already have moved branches when application is refused, so inspect their heads before retrying. The allowed gh-stack extension owns its rebases and atomic lease-protected pushes under the dispatcher's policy. A conflict restores branches through gh-stack and sends unchanged outstanding tasks to rework with the failure in their briefs. A changed branch also goes to rework and needs a new submission and gates; evidence for the old head remains historical.

Stacks require the GitHub repository setting and the gh-stack extension (v0.2.0 or newer). A missing extension (gh exits non-zero pointing at the gh-stack extension), a disabled stacks endpoint, or `gh stack` exit 9 falls back to ordinary dispatch for accepted dependencies. Submitted dependencies wait for acceptance when stacks are unavailable. If linking or merging becomes unavailable after dispatch, the branch is retained and the task is marked for ordinary merging: lower tasks must land before its PR can target main. A refused stack merge reports that fallback and the next merge uses the ordinary gate. Authentication and other unexpected failures are reported rather than treated as disabled stacks.

Stacks support only PRs in the same repository, one chain per stack, squash merges and no auto-merge or admin bypass. A repository requiring `--admin` uses the owner's `merge.admin` policy, `stack unstack ID`, then ordinary `merge ID` on the lower tasks first. Ordinary merges also accept `--method squash|merge|rebase` and retain `--match-head-commit`. Admin policy and other methods are refused for a linked stack. The webhook command consumes an already authenticated payload; it is not a public HTTP webhook receiver.

The owner can configure toolchain homes, writable caches and an environment file at project level, then override fields on a rung:

```sh
tower-crane project set --sandbox '{"write":["~/.cargo","~/.rustup"]}' --env '{"CARGO_HOME":"/home/user/.cargo","RUSTUP_HOME":"/home/user/.rustup"}' --env_file '~/.config/claude-code/bedrock.env' --scope '{"CPUQuota":"200%","MemoryMax":"8G"}' --agent owner
tower-crane ladder set hard --env_file '~/.config/claude-code/bedrock.env' --agent owner
```

`task add --lock lab/rdma --lock gpu/0 --environment lab` stores exclusive resource names and an informational environment label. Names are case-sensitive, trimmed and deduplicated. ## Event wakeups

`tower-crane wait [--after CURSOR] [--for NAME] [--task ID] [--types TYPES] [--timeout SEC]` blocks until the first matching event. Run this single command in your harness's background executor and act on its completion.

- `--after` is an event `id` or a byte `offset` returned by a previous wait. The default, `now`, starts at the log's current end; `0` replays from the beginning. Cursors are exclusive. A numeric cursor must be zero or immediately after a complete line, within the current log. Unknown ids and invalid offsets exit 2.
- `--for` defaults to `orchestrator`. `--task` restricts to that task, including comments and answers on decisions that block it. `--types` is a comma-separated list of event types. Filters are combined. The wait skips writes from its own agent identity, except events recorded as `owner` and engine observations (`worker-exited` and `stall`). Owner input must reach a waiter running as `owner`, and observations must wake their observer too.
- No timeout is imposed unless `--timeout` supplies seconds (fractions allowed). On timeout, stdout is `{"type":"timeout","offset":N}` followed by a newline and the exit code is 2. The offset follows the last complete line scanned, including filtered events. Interrupting the wait exits 130 and closes its watchers.
- An event line contains `id`, `type`, `to`, `at`, `agent`, `cmd`, `task`, `detail`, and `offset`. `offset` is the byte position after that event's newline. Use either returned cursor for the next wait to retain events that arrived while handling the first.

On startup or resume without a saved cursor, run `tower-crane wait --timeout 0` once. It exits 2 with a timeout and the current cursor, without observing worker exits or stalls. Save that offset, read state once, then start the background wait with `--after <offset>`. Events during the state read remain available, and the blocking wait observes current exits and stalls. With an explicit earlier `--after`, a zero timeout returns an already available matching event or a timeout cursor.

Every state change goes to `orchestrator`, including `submitted`, `accepted`, `rework`, `merged`, `worker-exited`, `spawn-fallback`, `stall`, `worker-message`, `owner-comment`, `decision-opened`, `decision-answer`, `owner-done`, `released`, and `evidence` (including review and gate results). `merged` requires successful merge evidence. Other changes keep their command name as the type; use `--types` to select a subset. Messages use their explicit recipient.

`tower-crane msg --to NAME [--task ID] TEXT` appends a message under the state lock. Its task defaults to `TOWER_CRANE_TASK`, otherwise null. The worker's identity is recorded; only the named recipient wakes.

Spawned harnesses deliver messages automatically through the adapters below. Messages are addressed to the generated agent name, across all tasks. `wait` remains the orchestrator's event interface.

| pi | Home extension appends context before the agent starts and to tool results | `agent_end` sends a message with `triggerTurn: true` |
| OpenCode | Home plugin binds to the dispatch's first chat session and appends text to its chat input and tool output | That session's `session.idle` starts another prompt; unrelated and child sessions leave its inbox alone |

| agy | No supported injection callback; messages stay queued | No stop veto or native session resume adapter yet |
| command | `TOWER_CRANE_HOOK` names a binding an adapter can use; otherwise messages join the next supported resume prompt | An adapter must implement its own live injection or stop veto |

`tower-crane hook ACTION --binding FILE [--payload JSON|-]` is the adapter write path. Actions are `inbox`, `tool`, `report`, `stop`, `git-push`, and `pr-created`. `-` reads JSON from stdin, keeping reports out of command arguments. Codex receives `-c bypass_hook_trust=true` for the generated hook commands; its filtered home omits project trust and user plugins, so repository hook sources stay disabled. A binding is generated at `homes/<agent>/hook.json` for each dispatch. It fixes the agent, task, state, harness and dispatch attempt; `--agent` and `--state` must match it, and owner identity is refused. Harness payloads cannot choose an identity, recipient or task. The bridge resolves only the invoking dispatch's binding from `TOWER_CRANE_STATE` and `TOWER_CRANE_AGENT`, refuses a mismatched `TOWER_CRANE_HOOK` or binding identity, and accepts no binding path argument. Hooks and shims invoke the shipped CLI by absolute path. Claude and Codex sandboxes deny reads of other agent homes, including homes created later.

`inbox` returns `{block:false, context:TEXT, ids:[event id, ...]}` and acknowledges only messages included in that context. Payload `ack:false` reads the pending context without acknowledging; a later `inbox` with `ids` acknowledges only those messages. OpenCode uses this sequence for idle delivery, acknowledging after `promptAsync` accepts the prompt. A rejection or SDK error leaves the messages queued for another idle event. A `stop` with unread messages returns `{block:true, context:TEXT}` and acknowledges the messages it used to hold the turn. Delivered ids persist in the event log across rebuilt homes. Dispatch and retry prompts acknowledge their included messages after launch; dry runs acknowledge nothing. When a process has already exited, the supervisor uses `stop` with `hold:false`, preserving unread messages for resume. Spawn refuses a command rung whose command argv contains neither `{prompt}` nor `{brief}`, including dry runs, because it cannot deliver the goal, task and house rules. Command adapters must consume `{prompt}` or `{brief}` for dispatch delivery and `{prompt}` for transient retry delivery; otherwise messages stay queued. agy currently lacks a native resume adapter, so its pending messages require an adapter before automatic delivery is possible.

Tool hooks and recognized JSON tool events publish `hook progress`, which the supervisor counts as claimant progress while renewing leases. The generated Git and gh shims publish `hook git-push` and `hook pr-created` after successful `git push` and `gh pr create`. The supervisor reads assistant reports from harness output and publishes a final message to `orchestrator` after stream closure. A stop without submit includes the last captured report, or says none was captured. Repeated stops with the same dispatch, report and submission state do not duplicate the message; a later result can supply a follow-up report. Plain tool output never counts as a report or nested event. Output observation ignores JSON lines larger than 1 MiB. Commands that bypass the PATH shims do not publish push or PR events.

`worker-exited` covers a spawned worker that exits without submitting, including failure before claiming. It includes `agent`, `pid`, `attempt`, `log`, exit `code` and log `size`; an existing claim remains for explicit recovery. Log text stays in the log file and is read live by `status` and `ready`. Detection uses `lib/processes.js`, shared with dead-spawn diagnostics. Local pid checks recognize Linux zombies and reused pids; another host's pid is never probed.

Automatic exit and stall observations run only for `owner`, `orchestrator`, an agent recorded by `spawn` with `role: orchestrator`, or a collector CLI whose visible parent is its recorded spawn monitor. Worker and reviewer `wait` calls consume recorded events without detecting exits or stalls. Their `spend --from-spawn` calls collect the requested usage without scanning peers. A sandbox can hide a live peer's pid, so its failed local probe cannot establish that the peer exited. Run the orchestrator and monitors where worker pids are visible.

For manual and legacy runs, `stall` means the claim lease expired and there has been no claimant progress for at least the most recently granted lease interval (`claim --lease` or `renew --lease`, defaulting to `limits.lease_minutes`). Claimant writes other than claim and renew count as progress. Renewing extends the lease but is not progress. Supervised spawns emit `stall` after `supervision.stall_ms` without progress paths, claimant writes or CPU activity, even while their lease stays live. Exit and stall events are deduplicated under the lock for the current claim and source; owner comments do not postpone a worker's stall.

The engine watches the state directory with `fs.watch`. A one-second internal stat and process fallback covers missed or unavailable notifications and detached exits, including Windows. The caller never queries in a repetition to discover completion.

Another browser needs a restart of serve and its new link;
- `content-type: application/json` and a body of at most 64 KiB;
- an `Origin`, if the browser sends one, of `http://127.0.0.1:<port>` or `http://localhost:<port>`.

serve answers any request only when its `Host` is `127.0.0.1:<port>` or `localhost:<port>`, so a page on another site cannot reach it through a name rebound to 127.0.0.1 and read the token.

`POST /api/ladder` body, with `harness` and `rungs` optional but at least one change, and `base` required:

```json
{
  "harness": "pi",
  "rungs": {
    "easy": { "harness": "", "model": "openai/gpt-5.5", "profile": "", "effort": "low", "args": "[\"--no-session\"]" }
  },
  "base": { "harness": "codex", "rungs": { "easy": { "profile": "luna", "effort": "medium" } } }
}
```

`base` is what the edit was made against: the default harness, and the own fields of each rung in `rungs` (as `ladder show` prints them, without `harness_from` and `from`, and with `harness` only when the rung names its own). If any of them differs from the state under the lock, the request is refused with 409 and writes nothing, so a form cannot undo a change made elsewhere with fields nobody touched.

Each rung lists the primary fields to change, as strings. An empty string clears the field; a field left out keeps its value. `args`, `command`, `tools` and `mcp` are JSON array text, as on the command line. The Settings view has no columns for `tools` and `mcp`; it keeps them as they are. Personal fallbacks are read from the user file and cannot be changed through this API. The whole request is one write: if it leaves a rung unable to run that could run before, nothing is written. The reply is `{ "ok": true, ... }` plus the resolved ladder (`harness`, `harness_from`, `user_file`, `user_file_exists`, `ladder`).

`POST /api/tiers` body: `{ "tiers": { "T1": "hard", "T4": "research" }, "base": { "T1": "medium", "T4": "medium" } }`, where `base` holds each task's tier as the edit saw it; a task whose tier differs now is refused with 409. All tiers are written in one write, or none. The reply is `{ "ok": true, "tiers": [{ "id": "T1", "tier": "hard" }, ...] }`.

Every successful reply also carries `version`, the state's version after the write, the same token the `reload` event for that write carries; the page uses it to tell its own write from one made elsewhere.

Both write under the lock, validate, log events (`ladder harness`, `ladder set` per rung, `task update` per task) with `"via": "serve"` and the agent serve runs as, and re-render the sketch. Refusals reply `{ "error": "<reason>" }`: 400 for a refused or malformed change (the reason is the one the CLI gives, prefixed with the rung or task it is about), 409 when `base` no longer matches the state, 403 for a missing or wrong token, a foreign origin or a foreign host, 404 for an unknown POST path, 405 for a method other than GET or POST, 413 for an oversize body, 415 for a body that is not JSON, 503 when the state lock is busy, 500 for anything else.

## Agents and worktrees

`spawn` passes an absolute `TOWER_CRANE_CONFIG` path to every harness, preserving the original user file when an isolated orchestrator dispatches workers. Command fallback executables containing placeholders are checked after expansion during preparation; `ladder show` defers their executable lookup until task context is available.

Before creating a new task branch, `worktree` fetches `base` from `origin` into `origin/<base>`, even when the remote's fetch configuration excludes that branch. It starts from the fetched commit when the local base is missing or is an ancestor of it. A local base that is ahead of or diverges from origin remains the starting point, with both commit SHAs reported on stderr; the local base branch is never moved. Task branches start from the selected commit SHA with no upstream branch. If origin has no such branch, it uses the local base and reports that fallback on stderr, or refuses if the local base is missing too. Without an origin remote, it uses the available local base or `origin/<base>`.

Prepare a dispatch with one `tower-crane worktree T1 T2 ...` call before starting workers. It validates every task id, fetches the base once if any task needs a new branch, then creates the worktrees serially from that selected SHA. With multiple ids, `--json` prints an array in task order; one id keeps the existing object output. Plain output lists one path per line. Duplicate ids are prepared once. A later dispatch fetches again; existing branches and completed worktrees remain usable offline. Start parallel `spawn` calls only after preparation, so they reuse the completed worktrees. Callers must serialize preparation within a repository, including calls from different worktrees or state directories; independent creation calls are not coordinated by a repository lock.

A `cannot lock ref` or `incorrect old value` fetch failure waits 100 ms and retries once before reading the tracking ref. Each fetch and missing-branch verification times out after 60 s. An unpack failure is usable only if a fresh origin read proves another caller already imported that exact tip. Other fetch failures, including a second ref-race failure, refuse before a task branch is created or recorded. Git worktree creation and checkout have no added timeout. Worktree creation uses Git's native initialization lock and unlocks only after checkout and its hooks finish. A killed or failed add leaves any surviving registration locked; `worktree` and `spawn` refuse to reuse it. If any task in a batch has an unfinished registration, the whole batch call refuses; worktrees prepared earlier in the call can remain. After Git and its children finish, inspect the worktree, then run `git worktree unlock <path>` for a complete checkout or `git worktree remove --force <path>` for an incomplete one. The CLI never reclaims that lock based on the parent's pid or elapsed time. `spawn` with an unprepared task uses the same single-task creation behavior, so run it serially.

`spawn` checks the rung, the brief (`brief set`) and the harness program (on `PATH`, or at the path the rung gives) before it creates anything. If the program still fails to start, or the lock cannot be taken, it records nothing and exits with the reason, naming the worktree it created; the worktree and branch stay, and the next spawn of the task reuses them. `spawn` never deletes a worktree or branch. The agent is named `<job>-<task>-<n>`, where the job is `worker` for the four tiers, `reviewer` for `review`, and the rung's name otherwise, numbered from earlier spawns of that job on that task.

Worker spawns check `limits.workers` under the state lock using the same count as `claim` and expired-lease `renew`: live leases plus unclaimed worker spawn reservations. A full limit exits non-zero naming the task and agent holding each slot, before launching a process, writing a home or recording spend. A successful dispatch records `reserved: true` and holds a reservation until the generated worker claims that task, an exit receipt or the monitor records that its supervised attempt ended, or one default lease passes since the attempt's last monitor record with no claim. Retry backoff keeps it until one lease after the scheduled relaunch; session receipts do not extend it, and a lapsed reservation is never revived. Claim consumes that worker's reservation without counting it twice. Launch failure holds no reservation. `--role review` and other non-worker rungs are unaffected; `--dry-run` only previews the command and reserves nothing.

`spawn exit` and `worker-exited` receipts release the matching unclaimed reservation. New receipts include `attempt`. Receipts without it match the latest preceding spawn, retry or fallback by task, agent and pid; the same match proves exit for resume, usage collection and recovery.

Reservations are read from the event log alone, so a sandboxed claimer and an unsandboxed spawner count the same holders. No process probe frees one, and hidden or unknown pids never do. Spawns recorded before reservations existed carry no `reserved` marker and hold no slot.

An expired pre-claim held by the generated worker is renewed to the default lease duration under the spawn lock, preserving its agent, `since` and `from`. This lease holds the slot before the supervisor can renew it. A failed launch leaves the pre-claim and receipts unchanged.

Worker dispatch and role-filtered `brief get` use the shared text of briefs without role headings. For role-specific text, use level-two headings `## Shared`, `## Worker` and `## Reviewer`. Matching is case-insensitive, and headings inside fenced code blocks are ordinary text. Text before the first role heading is shared, and each section ends at the next role heading. `## Rework notes` starts a shared section. The worker prompt includes shared text and the `Worker` section; the reviewer packet includes only the `Reviewer` section alongside the diff, acceptance and gate results.

```md
## Shared
Constraints and task context for both roles.

## Worker
Implementation instructions.

## Reviewer
Review instructions.
```

For worker and reviewer jobs, a `claude`, `codex`, `opencode` or `agy` prompt starts with the body of the matching `skills/tower-crane-work/SKILL.md` or `skills/tower-crane-review/SKILL.md`, with frontmatter removed. If that `SKILL.md` is missing, `spawn` warns on stderr and continues without the role skill. A fresh prompt then contains a `## Goal` section (the project goal, the task's target, and an instruction to restate both in the first message), a `## House rules` section listing the rule files by path ([Agent files and homes](ladder.md#agent-files-and-homes)), the worker brief or reviewer packet, the task's id, title, acceptance and kind as JSON, and a line telling the agent to use the `tower-crane` CLI for every state change. It says `you are not the owner; never pass --agent owner`. Its closing instruction says `run tower-crane with --agent <name> if TOWER_CRANE_AGENT is missing`, using the same name passed in the environment. A resumed worker gets its rework note without another copy of the skill body. A pi worker or reviewer receives its matching skill through `--skill` instead, without a duplicate in the prompt; if its `SKILL.md` is missing, `spawn` warns on stderr and omits `--skill`. A fresh custom `command` rung receives the worker brief or reviewer packet and task prompt without an automatically embedded skill body. Its `{brief}` argument is a temporary copy of that context with the same `## Goal` and `## House rules` sections first and the task JSON after it, so an adapter that reads only `{brief}` still gets the goal, rules and acceptance; the copy is removed after foreground completion or a verified background exit. The prompt runs in the task's worktree, which is created if missing; `--dry-run` creates nothing. Both streams go to `logs/<task>-<agent>.log`; the `spawn` event records the harness pid and dispatch metadata. In the background the agent is detached and a monitor collects usage after exit through the same locked observer used by `wait`. A waiter that observes an exit also attempts collection; concurrent observers count the spawn once. With `--wait` output is also streamed to the terminal (stdout goes to stderr under `--json`), usage is collected after stream closure, and tower-crane exits with the agent code.

`spawn --role review` selects a reviewer per task and requires a submitted head with passing software gates, including CI for a PR. It checks again under the dispatch lock and refuses a second live reviewer at that head and revision. Review prompts contain the diff, acceptance, gate results and the brief's `## Reviewer` section. They ask the reviewer to use the supplied results and re-run tests only for a focused probe. The CLI writes `reviews/<task>-<full-sha>.md`; packets over 12,000 characters are referenced from a short prompt so Windows command limits do not drop the diff. `rung` stays `review` for role and spend accounting; `review_rung` names the selected tier or fallback, and review dispatch adds the submitted `sha` and `revision`. An unsubmitted `--dry-run` previews the fallback command only; a submitted dry run checks gates and selection but writes no packet.
Spawn logs are created exclusively with mode `0600` on POSIX. On Windows, logs inherit the state directory's ACL; the state directory normally lives under the user's profile. An occupied log name, including a leaf symlink, refuses the spawn without writing to the file or recording a spawn. Move the occupied log before retrying. The state directory and its parent directories remain trusted local storage.

Review diff reads run before the spawn state lock. Inside the lock, a changed submitted SHA or configured base refuses dispatch with a retry instruction. Gates, reviewer selection and duplicate detection use the state read under that lock.

Every rung gets a fresh, private `homes/<agent>/` with hook bindings and Git and gh shims, built under the lock before the agent starts. Homes of exited agents are removed. For claude and codex, `spawn` also renders the agent file of the rung's job (`agents/tower-crane-worker.md` for the tiers, `tower-crane-reviewer.md` for `review`, `tower-crane-small.md`, `tower-crane-orchestrator.md`) into flags. Their `HOME` is the home's `home/`; other harnesses retain their existing HOME and authentication setup. Every harness's `PATH` starts with the generated shims. The rung's `tools` and `mcp` opt back in to what the file leaves out; an MCP server the user's harness config does not define refuses the spawn, `--dry-run` included. [Agent files and homes](ladder.md#agent-files-and-homes) has what each harness gets.

Codex roles with `gitPush: branch` receive an explicit `git push` allow rule so branch publishing does not need an approval prompt. Force prefixes remain forbidden, and the git shim checks options, refspecs and remote configuration. Roles with `gitPush: none` receive no push authorization.

`spawn` also records the host and, on Linux when available, the process start time in clock ticks. `status` and `ready` match the most recent spawn to the current claim's agent, including workers that claim after starting. An exited process is reported as `exited without submit`, with the pid, log path, the last 20 log lines within the final 8192 bytes, and guidance to release with a reason. Neither view prints a command that supplies owner identity. The engine rechecks exit under the lock before another agent can recover it. A live or unverified process still requires the claimant or an explicit owner. The tail is bounded so a large harness log cannot overwhelm a status check. A missing or unreadable log is reported without hiding the exit. Foreground spawns retain their logs; legacy events with a null log report `foreground output; no log`.

After `rework`, `spawn --task ID` resumes the last submitting Codex worker's recorded session when its resolved rung and worktree still match. Codex runs `codex exec [-p PROFILE] resume --json <thread> <note>`. Model, effort and extra rung arguments still apply. Native Claude starts fresh because the measured resume rewrote its conversation cache. Both paths include a note with the rework reason and failed review summaries and refs for the submitted head and current revision. Session ids travel in harness arguments and spawn receipts, never in the note or brief.

Resume keeps the worker's agent name. If submission cleared its lease, spawn restores its claim with the original `since`, a new default lease, and `from: rework` before dispatch. A live claim already held by that worker stays unchanged. An expired claim needs a worker slot before its lease is restored. Blockers and the worker limit still apply. The resumed worker can submit directly. A different claimant or a running or unverified prior process refuses resume with a recovery command. A foreground exit receipt proves that attempt exited even if the OS reused its pid; an earlier attempt's receipt does not. Before an isolated Codex resume, spawn checks for the recorded rollout under `homes/.codex/<agent>/sessions`. If the rollout is missing, spawn starts a fresh numbered worker with the full brief and review note and records `resume_fallback_reason` in the spawn event. If the previous worker holds a live rework claim, spawn transfers it to the fresh worker; an expired claim must pass the blocker and worker-limit checks before transfer. If preparation or launch fails before a child starts, spawn restores the prior claim under the lock so the attempt can be retried. Missing session records, a changed rung configuration or harness, or a moved worktree also start a fresh worker. Fresh workers without a transferred claim claim normally. Reviewers always start fresh.

Codex's `--json` output supplies `thread.started.thread_id`; Claude's JSON result supplies `session_id`. A command harness can substitute `{session}` in its argument array (empty for a fresh spawn) and emit either native session record to exercise the same path. A resumed attempt gets its own `logs/<task>-<agent>-attempt-<n>.log`; earlier logs stay intact. The existing detached usage monitor records the first session id while the harness runs. Re-dispatch can recover the receipt from that attempt's log if the monitor has not recorded it yet. `--wait` records the session at stream closure. `--dry-run` prints the selected fresh or resume command and never writes a claim or receipt. Cache measurements and their limits are in [resume-cache.md](resume-cache.md).

`lib/spawn-session.js` exports `eligible(dispatch, cwd, events)` for dispatchers such as provider fallback. It returns `{ id, agent, previous }` only for an eligible native Codex route or command adapter. It returns null for a fresh route and refuses a matching session whose prior process has not exited or whose claim belongs to another worker. The helper compares route values without depending on object key order. It does not build prompts or change state.

Usage receipts remain separate per resumed attempt, keyed as `spawn:<agent>:attempt:<n>`. Re-dispatch collects the previous attempt before starting the next. Codex's counters are cumulative, so dispatch records `usage_before` and collection subtracts those counters for the resumed attempt. A missing baseline leaves its usage unknown. Claude's result usage describes the current invocation and needs no subtraction. Repeated collection updates the same attempt instead of adding it twice.

The existing spawn monitor supervises the harness and renews its claim halfway through each lease while the process runs or waits for a rerun. Transient exits (75, SIGTERM, SIGINT, harness-level provider 5xx/outage, and harness error records reporting 429, rate limits, temporary unavailability or overload) retry the same generated agent, route and worktree. Codex and command adapters resume with a short interruption note; Claude reruns fresh with a new session id, the brief and the note, following `lib/spawn-session.js`. Agent messages and tool output cannot trigger an outage retry. `ladder set RUNG --supervision JSON` configures `{ retries, backoff_ms, max_backoff_ms, stall_ms, progress_paths }`; `--clear supervision` restores the defaults. Defaults are five reruns after 30, 60, 120, 240 and 480 seconds, totaling 15 minutes 30 seconds, a ten-minute delay cap for larger budgets, and five minutes without progress and CPU activity before a stall. State is cached until the event log changes; progress and CPU are sampled once per second. Child exits and pipe closure wake the monitor immediately. See `docs/state.md` for the measured outage behind this budget.

Set `ladder.easy.fallbacks` in the user file to `[{"profile":"sol","effort":"high"}]` to add an ordered personal fallback list. It applies over every project's easy primary. Project `--fallbacks` is removed with no compatibility path. `ladder show` identifies the user-file source and reports unavailable routes; the supervisor skips them, including missing executables, incompatible harness fields, missing models and unavailable Codex profiles. These checks are local; provider access is not queried. A provider outage switches only after the current route exhausts its same-route reruns. A structured harness policy refusal switches immediately, including a successful exit reporting refusal. A switch keeps the agent, claim and worktree, rebuilds its isolated home and starts a fresh session with the original brief. It never resumes across models, providers or harnesses. Retry counters reset per route, and `spawn-fallback` wakes the orchestrator with the previous and new route, pid, session and reason. Spend is collected separately for each route; repeated collection is idempotent. Rework after a route switch starts fresh. The fallback routes inherit the primary harness and supervision unless they override them; research Claude fallbacks also inherit the primary `web_mcp` unless they specify their own server. Other harnesses do not inherit it. An inherited or explicit web MCP cannot combine with `mcp`; other fields are independent. No fallback is enabled by default; remove the field or set `[]` in the user file to disable it. See `docs/state.md` for the accepted refusal envelopes.

Every natural agent exit on POSIX terminates its process group, including background processes the agent left running. Stopping the monitor uses the same path: SIGTERM, then SIGKILL after a five-second cleanup grace period. Windows uses `taskkill /T /F` while the harness is live; a natural exit never sends a tree kill to its released PID. A POSIX retry waits for the previous process group to stop; every retry waits for output pipe closure.

Spawn sets `TOWER_CRANE_SANDBOX=1` for sandboxed claude and codex roles, otherwise `0`, replacing an inherited value. Only sandboxed board browser tests add `--no-sandbox` and `--disable-dev-shm-usage` and redirect browser HOME/config/cache/temp into their temporary profile. Host runs retain their original environment and flags, including the existing root `--no-sandbox` exception. Run `TOWER_CRANE_LIVE_BROWSER=1 node --test test/live-browser.test.js` from an unsandboxed Linux session to check one board browser test through a real worker on each harness. See [ladder.md](ladder.md#agent-files-and-homes) for browser isolation and probe options.

Every agent launch removes `NODE_TEST_*` variables after merging inherited, project, rung and env-file values, including retries and fallback routes. This clears the outer Node test runner's context so an agent's `node --test` executes its files. Other environment values remain in effect.

`status`, `task show`, rendered sketches and serve show `running`, `retrying N`, `waiting`, or `blocked: text`. Status JSON has `runs: [{ id, run }]` and each in-progress entry has `run`; task-show JSON has `run` or null. A run awaiting retry keeps its lease and is not reported as exited. Only the final exit becomes recoverable. A stall changes the phase and emits its event without killing the process; progress restores running. Successful exit waits for the next workflow step; submit clears the phase. A provider outage before a supported session exists reruns fresh on the same route when a fallback list is configured. Other transient exits without supported sessions block.

Both commands return an `exited_claims` array under `--json`, with `{ id, agent, pid, log, code, size, tail }` entries (empty when none). `code` is the recorded exit code or null when signaled or unknown; `size` is the log size in bytes or null when unavailable. The views only read state. The claim counts toward the workers limit while its lease is live; the supervisor handles renewals and transient reruns. Terminal claims stay held until release or expiry. Any agent may release a verified exited claim; release records the caller's reason and only the pid, log path, exit code and log size, and makes the task available again. Log tails are read live by the views and never copied into task notes or release events. Submitted tasks, manual claims without a matching spawn, and spawn records from a previous claim are excluded, including an expired lease reclaimed under the same agent identity.

Local process checks ignore a spawn recorded on another host and treat permission errors or unavailable Linux process metadata as unknown, rather than as proof of exit. On Linux they recognize zombies as exited and distinguish a reused pid by its recorded start time. Older spawn events without a host are treated as local. On other platforms an exit is detected when the pid no longer exists or a foreground `spawn exit` event records it. The detached usage monitor stops after successful collection or project removal. It logs a recovery command and exits with code 1 after 10 min of failed collection or continuously unknown process observations. A known live process is watched until exit.

### Usage sources and limits

`lib/usage.js` exports pure `parseUsage(harness, log, sessionText)` for exit handling. File access is in `lib/usage-files.js`; no parser reads credentials. Both streams have a durable log, including foreground output. Foreground collection waits for stream closure; a detached monitor collects background usage through the CLI. The original harness pid remains the job identity.

| Harness | Captured usage |
|---|---|
| `codex` | The last cumulative `token_count.info.total_token_usage` in the exact session named by `session id` or JSON `thread.started` supplies input, cached input, output and total. Only matching `rollout-*-<id>.jsonl` files under the recorded `CODEX_HOME/sessions` are opened. Repeated totals are counted once. JSON `turn.completed.usage` is supported. The text `tokens used` footer excludes cached input, so it cannot supply the inclusive total when structured usage and session detail are unavailable. |

Native agents use one call, for example `tower-crane spend T1 --tokens 100 --input 80 --cached 60 --output 20 --rung easy --harness claude --model opus --agent native-T1-1`. `cached` is part of `input`, not added to total again. Components are optional; supplied counts must fit total, and cached cannot exceed input when supplied. Record native usage once per completed dispatch. Do not record spawned tokens manually as well as automatically. An unavailable native counter is a task note, not an invented zero.

## Gates

Each gate runs software, then records evidence on the task. Only `check tests`, `check clean`, `check sources`, `check ci` and `merge` record their respective software evidence types. Each result carries `source` naming that command and `commands` listing the processes it ran, with their arguments, working directory, exit status and signal. This includes the test command at head and, in `prove` mode, without the change, the cleanup invocation, GitHub queries and the merge invocation. Expensive proof records the full head run and both scoped runs. Tests mode `none` records only the Git command verifying the submitted commit and names the skip policy in its summary. Tests evidence and audit detail record the resolved `tests_mode`; successful tests evidence with a missing or mismatched mode no longer counts against the current project policy. A precondition failure can have no commands; an ok entry needs at least one command to count. The audit event carries the same receipts and revision.

For the `check tests` run without the code change in `prove` mode, changed declarative manifests, lockfiles and `tests.keep` matches stay at the submitted sha. This includes files such as `package.json`, `package-lock.json`, `Cargo.toml`, `Cargo.lock`, `go.mod`, `go.sum`, `pyproject.toml` and `requirements*.txt`; executable build files such as `Makefile` need an explicit keep glob. The summary names each kept path.

The gate itself lives in `lib/gates/<name>.js` and exports `async run(ctx)` returning `{ ok, summary, ref?, sha?, receipt? }`, where `ctx` is `{ root, worktree, task, project, args, log, exec }`. Gates run commands through the shared helpers in `lib/gates/common.js`, which use the CLI's `exec` to capture receipts. The CLI runs the gate without holding the lock, then records the result as evidence of the gate's type by `--agent`, at the returned `sha` or the submitted one, against the revision the gate started on. A local CI `receipt` is copied into evidence and its audit event. Hosted CI records `ci_policy` from the project settings when the check starts, in both evidence and the audit event. A gate that reports `ok: false` exits 1 after recording. A missing gate module exits 1 with "gate not installed".

Acceptance counts software evidence only when events.jsonl has a matching gate event: `cmd === source`, the same task and agent, and matching type, source, exact evidence sha, verdict, revision and command receipts. It ignores entries without that event and ok entries with no commands. Writes separate an unterminated audit-log tail from new events so a torn line cannot hide a gate receipt. Existing entries stay readable; run the gates again for the submitted sha to replace their proof. Merge and the task views use the same check. Waivers for review and software gates count only when their agent is `owner`.

Tests and clean evidence and their audit events carry `gate_policy`: `{tests_cmd, tests_proof_cmd}` for tests or `{clean_cmd}` for clean, captured when the check starts. Values are trimmed strings or null. Missing, malformed or changed policy makes previous evidence stale, even if the owner changes commands during a run. Successful receipts must also include the pinned test command (except none mode) or the pinned cleanup invocation with its appended arguments. Scoped proof records `receipt.proof_tests`, the changed test paths used to expand the pinned template; every test shell receipt must match the full command or that expansion. Acceptance, merge and task reports use the same check. Old receipts without this snapshot require a new check; owner waivers retain their existing behavior.

The CLI refuses manual software verdicts, and software receipts require matching records in tasks.json and events.jsonl. Plain files cannot stop a writer running as the same user from forging those records or an owner waiver. The owner pins test and cleanup commands; acceptance compares their recorded policy and command receipts with the pins. Reviewers check that the configured runners verify the change.

`check sources` scans HTML without using tag replacement expressions. It preserves inline punctuation, skips nested comments and templates plus script/style blocks, and excludes unfinished or ambiguous markup from quote matching. Its pinned DNS lookup supplies all validated public addresses for IPv6/IPv4 fallback within the same page deadline. See [Research sources](state.md#research-sources) for the deliverable and fetch limits.

Ordinary `merge` defaults to `--method squash`, with the task title as the commit subject and its acceptance lines joined by newlines as the body. `--subject` and `--body` override these independently, preserving multiline text and an explicitly empty body. A subject must be non-blank. `--method merge` uses the same commit text options; `--method rebase` omits them and refuses explicit subject or body overrides. Every ordinary merge invocation uses GitHub's full head SHA with `--match-head-commit` after verifying it matches the accepted SHA. Branch deletion is requested unless `merge.keep_branch` is true. Only owner-set `merge.admin: true` adds GitHub's admin option for solely owned repositories. There is no one-off `merge --admin` flag; acceptance, review, CI and head checks still apply. Stacks use the guarded atomic merge described under Run.

Configure review caps in project.json, for example `"ci": { "capped_review": [{ "app": "revuto-review", "pattern": "reached the \\d+-round review limit" }] }`. `app` is the exact GitHub app slug without surrounding whitespace; `pattern` is a case-insensitive regular expression searched across the check output title and summary. Output text is not searched because review findings can quote a cap message. Only completed runs with conclusion `failure` qualify. A failed suite qualifies only when it is linked to a matched run and its complete set of runs is green or capped. At least one run outside ignored apps and matched caps must exist; a capped review alone does not prove CI ran. Other failures from that app and all unfinished checks still block. Missing configuration grants no exception; malformed rules fail the gate. The independent review gate remains required.

Hosted CI reads `headRefOid,mergeable,mergeStateStatus` with `gh pr view` before fetching checks. A `CONFLICTING` PR or `DIRTY` merge state fails with a conflict diagnostic because GitHub does not run `pull_request` workflows on conflicting PRs. Unknown or missing mergeability fails with an instruction to retry later. A mergeable PR may still have a `BLOCKED` merge state while waiting for checks or reviews; the CI gate checks its runs and suites independently. Without a task PR, the gate checks only the submitted commit. `ci.required` defaults to empty; malformed lists fail closed. Required runs cannot be satisfied by ignored apps or capped failures. These hosted policies do not change local CI.

Hosted `ci_policy` contains the effective `required`, `ignore_apps` and `capped_review` arrays, defaulting absent or null fields to `[]`. Only the `app` and `pattern` fields of capped rules affect the snapshot. Invalid policy records `null` on the failed check. Audit events must match the evidence policy. Acceptance, merge and task gate reports refuse an unrecorded policy, a malformed current policy or a snapshot that differs from the current project. A stale pass requires a new `check ci`; acceptance does not rerun an already attempted gate automatically. Other `ci` fields do not affect the snapshot. Once an audited merge succeeds at that head and revision, reports keep its recorded CI result.

Local CI needs a Git version that supports `merge-tree --write-tree`. It reads the current local base and `origin/<base>`, choosing the remote ref when it contains the local base or the local base is absent, as dispatch does. `check ci` does not fetch; refresh the base refs before checking when needed. Before merging with a local receipt, `merge` fetches the base from origin into `origin/<base>` with a 60 s timeout, even if origin's fetch configuration excludes it. A failed fetch or a fetched base different from the receipt's `base_sha` refuses the merge. Run `tower-crane check ci ID` again after the base moves. Repositories without origin still validate against their local base. The command runs in a temporary detached worktree under `TOWER_CRANE_TMP` (or the system temp directory). HEAD stays at the submitted commit, while the index and tracked files contain the merge result. Conflicts fail before the command runs. Missing commands, nonzero exits, signals, timeouts, tracked-source changes and a merged tree that moves during execution fail. The process group is stopped on exit or timeout and the worktree is removed on every outcome. A head that edits the checker edits its own gate; reviewers must inspect checker changes.

Only the gate runner produces the local receipt. It records `variant`, `command`, `timeout`, `exit`, `signal`, `head_sha`, `base_sha`, `tree_hash`, `source_digest` and `duration_ms`; see state.md for the digest definition. `variant` is `default`, `kind:KIND` or `task:ID`. Acceptance, merge and task gate reports require the audited receipt to match the submitted head, the current merged tree and the resolved variant, argv and timeout, with exit 0 and a matching command execution. A new head, changed merge result, variant, command or timeout needs a new check. Different variants cannot share receipts even with identical argv and timeout. Earlier receipts without a variant need a new check too. Changes to an unselected kind mapping do not invalidate a task override. Once successful audited merge evidence exists for that head and revision, these reports keep the recorded CI result without recomputing the current merged tree, and a repeated merge skips the base fetch. Untracked build outputs do not change the tracked source identity. Local CI does not query hosted checks or require `project.repo`; absence of `ci.local` keeps hosted behavior.
