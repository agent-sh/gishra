# State

gishra keeps a project's plan and progress in plain files. People and dashboards read them; only the `gishra` CLI writes them, under a lock, after validation. An agent that needs to change state runs a command.

## Where

The state directory is the first of:

1. `--state DIR` on the command line
2. `GISHRA_STATE` in the environment (`gishra spawn` sets it for every agent it starts)
3. `.gishra/` at the root of the main checkout, found through `git rev-parse --git-common-dir`, so every worktree of the repo shares one state

`gishra init` adds `.gishra/` to `.git/info/exclude`. State is not committed unless the project chooses to. In a bare repository, `.gishra/` sits inside the common git directory.

Commands that need the repository (`worktree`, `spawn`, the gates) use the one gishra runs in; outside a repository, the one that holds the state directory.

## Files

| File | Holds |
|---|---|
| `project.json` | name, goal, repo, base branch, roles, limits, budgets, standards profile |
| `tasks.json` | every task and its status, evidence and spend |
| `decisions.json` | questions for the owner and their answers |
| `briefs/<task>.md` | the context a worker gets for that task, kept current by the orchestrator |
| `events.jsonl` | append-only log of every change, with time and agent |
| `sketch.md`, `sketch.html` | rendered views; regenerated by `gishra render` and after every write |
| `lock` | advisory lock file; never edit |
| `logs/<task>-<agent>.log` | output of agents started by `gishra spawn` |

All JSON files carry `"version": 1`. Writes go to a temp file in the same directory and are renamed into place. A command that is refused writes nothing.

### Lock

A write creates `lock` exclusively, holding the writer's pid, host and time. Another writer waits up to 10 s, then exits 3. A lock is stale when its holder process is gone (same host) or the file is older than 60 s; the next writer breaks it. Reads take no lock.

## project.json

```json
{
  "version": 1,
  "name": "billing-retry",
  "goal": "Retries on payment webhooks are idempotent and observable",
  "repo": "acme/billing",
  "base": "main",
  "standards": "default",
  "roles": {
    "orchestrator": { "harness": "claude", "model": "claude-opus-5-5" },
    "worker":       { "harness": "codex",  "profile": "sol" },
    "reviewer":     { "harness": "claude", "model": "claude-opus-5-5" },
    "small":        { "harness": "codex",  "profile": "luna" }
  },
  "limits": { "workers": 6, "lease_minutes": 60 },
  "budget": { "hours": 40, "tokens": 20000000 }
}
```

`gishra init` writes the roles shown above, `limits` as shown, and `budget` values of `null` (no budget) until `gishra project set` gives them. `repo` defaults to the GitHub slug of the `origin` remote, `base` to the branch checked out in the main checkout.

A role names a harness and a model or harness profile. `harness` is one of `claude`, `codex`, `opencode`, `agy`, `pi`, or `command` with a `command` array (`{task}`, `{brief}`, `{prompt}` and `{cwd}` are substituted; `{brief}` is the brief file's path). Optional role fields:

| Field | Applies to | Meaning |
|---|---|---|
| `model` | all but `command` | model id; pi also takes `provider/id` |
| `profile` | `codex` | codex config profile |
| `provider` | `pi` | pi provider name |
| `effort` | all but `opencode` and `command` | reasoning effort, in the harness's own terms (agy: low, medium, high, max; pi: off, minimal, low, medium, high, xhigh, max) |
| `args` | all | extra arguments appended verbatim to the command |

docs/cli.md lists the command each harness gets.

`standards` is `default` (the profile shipped with gishra) or a path to a Markdown file. A path is checked for readability and recorded relative to the repository root; only the default gates apply for now.

## tasks.json

```json
{
  "version": 1,
  "next": 4,
  "tasks": [
    {
      "id": "T1",
      "title": "Idempotency key on webhook retries",
      "kind": "code",
      "acceptance": ["a retried webhook with the same key is processed once", "test proves it"],
      "depends_on": [],
      "needs_owner": null,
      "size": "M",
      "role": "worker",
      "status": "todo",
      "claim": null,
      "branch": null,
      "pr": null,
      "sha": null,
      "evidence": [],
      "submitted_by": null,
      "revision": 1,
      "spend": { "minutes": 0, "tokens": 0 },
      "notes": []
    }
  ]
}
```

- `kind`: `code`, `docs`, `research`, `design`, `ops`.
- `size`: `S` (under an hour), `M` (a few hours), `L` (a day). Anything larger is split; `validate` reports it.
- `needs_owner`: null, or the reason the owner has to act (a credential, a purchase, a product call). Such a task is never ready on its own; the owner clears it with `gishra owner-done`.
- `status`: `todo`, `in_progress`, `submitted`, `accepted`, `rework`, `cancelled`. `ready` and `blocked` are computed, never stored.
- `claim`: `{ "agent": "w-3", "since": "...", "until": "...", "from": "todo" }` while in progress; `from` is the status before the claim (`todo` or `rework`), which `release` restores. An expired lease frees the task: it counts as `from` again and another agent may claim it. Until someone does, the original claimant can still renew or submit.
- `submitted_by`: the agent that submitted the current `sha`.
- `evidence`: entries `{ "type", "ok", "sha", "agent", "at", "summary", "ref", "revision" }`, plus `"waived": true` on an owner waiver. Types: `tests`, `clean`, `review`, `ci`, `merge`, `note`.
- `revision`: incremented when acceptance or dependencies change; evidence recorded against an older revision does not count.
- `notes`: `{ "at", "agent", "text" }` entries. The orchestrator folds what matters into the brief. A note starting with `split:` on an `L` task records why it stays whole.

The CLI never writes a dependency on a task that does not exist, a dependency cycle, or a task without acceptance. `validate` still checks files edited by hand.

### Ready and blocked

A task is ready when its status is `todo` or `rework`, every dependency is `accepted`, `needs_owner` is null, and no open decision lists it in `blocks`. Otherwise `gishra ready --all` says what blocks it.

Ready tasks come in priority order: most outstanding dependents (direct or transitive, not yet accepted or cancelled) first, then by id.

### Acceptance gates

`gishra accept` refuses unless the task's current revision has, at the submitted `sha`:

- `code` tasks: `tests` ok, `clean` ok, `review` ok from an agent other than the one that submitted, and `ci` ok when the task has a PR
- other kinds: `review` ok from another agent

A gate passes when the latest evidence of its type for the current revision, at a sha matching the submitted one, is ok. Shas match when one is a prefix of the other and the shorter has at least 7 characters. For `review`, entries by the submitter are ignored.

The standards profile may add gates. `--waive TYPE --reason TEXT` records an owner waiver as evidence; only an agent named `owner` can waive. A waiver satisfies its gate. If the accept is still refused, the waiver is not recorded.

## decisions.json

```json
{
  "version": 1,
  "next": 2,
  "decisions": [
    {
      "id": "D1",
      "question": "Store idempotency keys in Redis or Postgres?",
      "options": ["redis", "postgres"],
      "recommendation": "postgres",
      "why": "keys must survive a Redis flush; volume is 30/s",
      "blocks": ["T3"],
      "status": "open",
      "answer": null,
      "note": null,
      "asked_by": "orchestrator",
      "asked_at": "...",
      "answered_by": null,
      "answered_at": null
    }
  ]
}
```

A decision blocks only the tasks it lists. Everything else keeps running. `status` is `open` or `answered`. When options are listed, the answer must be one of them. Answering adds a note with the answer to every task the decision blocked.

## events.jsonl

One JSON object per line: `{ "at", "agent", "cmd", "task", "detail" }`. `cmd` is the command name (`task add`, `claim`, `spawn`, `check tests` and so on); `gishra spawn` also counts its earlier `spawn` events to number agents. `gishra status` and the sketch read time and token spend from tasks; the log is for audit and recovery.
