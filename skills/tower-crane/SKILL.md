# tower-crane: orchestrate

Arguments: `$ARGUMENTS`. If `tower-crane` is not on PATH, say how to install it (`npm i -g @agentsys/tower-crane`) and stop.

Use `TOWER_CRANE_AGENT` or `orchestrator` as your identity; pass `--agent <name>` on every tower-crane call unless a step names another actor.

- `status`: run `tower-crane status` and `tower-crane decisions --open`, show them and name `sketch.html` in the state directory, then stop.
- `decisions`: run `tower-crane decisions --open`, show options and recommendations, record any owner answer with `tower-crane answer <id> --choice "<option>"`, then stop.
- Otherwise, follow the orchestrator procedure below.

You plan, dispatch, check and merge; workers write the code and reviewers judge it. Keep your context to the plan and briefs.

All state goes through the `tower-crane` CLI (`tower-crane --help`). Never edit `.tower-crane/` files by hand. The standards to follow are in `standards/default.md` of this plugin unless `project.json` names another profile; read it once at the start.

## 1. Intake

- Read what was handed over: the issue (`gh issue view`), the goal text or the plan file. Read the repository's `AGENTS.md` and README, then only the code you need to plan.
- If a question changes what gets built, ask it now. Anything narrower becomes a queued decision later.
- If there is no state, `tower-crane init --name <short-name> --goal "<one sentence>" --repo <owner/name> --base <branch>`. Before reading state on startup or resume without a saved cursor, run `tower-crane wait --timeout 0` once; exit 2 is expected. Save its JSON `offset`, then read `tower-crane status` and `tower-crane decisions --open` once. Do not re-plan what is accepted. The next blocking wait starts at that cursor, keeping events that arrive during the state read.
- Check the ladder with `tower-crane ladder show` (`docs/ladder.md` of this plugin explains it). Use what the owner configured; the `orchestrator` rung is you.
- Operational settings are yours to change under your own identity: gate commands, CI and tests policy, worker and lease limits, ladder models and tools, review policy, task kind and tier, `owner-done`, and `accept --waive review` for a reviewer capped (in `check ci`) or down (its spawn exited without a verdict) at the submitted head. Owner-required ones (`merge.admin`, sandbox, env and scope grants, rung commands, moving a worker, reviewer or small rung off claude and codex or giving args to another harness, budget raises, orchestrator spawns, other waivers, anything published outside the repo) refuse and open a decision for the owner; wait for its answer. `docs/state.md#authority` of this plugin has the table. `check` and `accept` pin a missing test or cleanup command they can detect.

## 2. Plan

- Split the goal into tasks a single agent finishes in hours: `S` under an hour, `M` a few hours, `L` a day at most. Split anything bigger.
- Every task has acceptance a reviewer can check from the diff and the gate reports. "Works" is not acceptance; "a retried webhook with the same key is processed once, shown by a test" is.
- Add a dependency only when the work really needs the other result. Fewer edges, more parallel work.
- Give each task a tier: `easy`, `medium`, `hard` or `research`. Kind and size pick a default (`research` kind is research, else `S` easy, `M` medium, `L` hard); pass `--tier` when the risk differs from the size, such as a small change to a security boundary (`hard`) or a large mechanical rename (`easy`).
- Mark `--needs-owner "<what and why>"` on anything only the owner can do: credentials, payments, product calls, messages to people outside.
- Write the plan with `tower-crane task add` or `tower-crane plan import`, then `tower-crane validate` until it is clean.
- Write a brief for every ready task (`tower-crane brief set ID -`). A brief is the whole context the worker gets, so it is exact and short (under about 60 lines): the task's goal, the files and interfaces involved, decisions already made, constraints from the standards that matter here, how to verify, and the test command. No repository tour, no history.
- Include the plugin's absolute worker skill path in the brief: `worker: read and follow <abs>/skills/tower-crane-work/SKILL.md`. Spawn supplies reviewers with the matching skill and a separate diff and gate packet; native reviewers need the absolute review skill path passed with their context.
- `tower-crane render` and tell the owner where `sketch.html` is.

## 3. Run

Act on events until every task is accepted or cancelled, or the only open work is waiting on the owner.

- **Dispatch rule.** A worker runs on the rung of its task's tier. Review dispatch selects an independent model from the tier, diff risk and measured median review cost, with the `review` rung as fallback. A rung on claude, codex or pi always runs through `tower-crane spawn`, even when that is your own harness: spawn gives the agent its own environment and agent file, while a native subagent shares your session's memory, settings, hooks and MCP servers and cannot be isolated. Pi isolates configuration and tools but has no command sandbox or MCP support; moving a sandboxed role to pi needs the owner. Only a rung on another harness may run as your native subagent, when its harness is yours; map its model to your Agent tool's names.
- **Workers.** `tower-crane ready`. Choose a wave within `limits.workers` and prepare it with one `tower-crane worktree ID [ID ...]` call before starting any workers. This fetches the base once and creates worktrees serially. Do not run worktree creation or unprepared spawns concurrently in the same repository. Run `tower-crane spawn --task ID` without pre-claiming; it runs the tier's rung and the worker claims as the generated `TOWER_CRANE_AGENT`. A native worker (another harness only) gets a unique name, `tower-crane claim ID --agent <name> --lease MIN`, and that name, task id, absolute worktree and state paths, skill path and brief. A worker that reports its task is harder than its tier gets re-tiered (`tower-crane task update ID --tier T`) before the next dispatch.
- **Wakeups.** After each dispatch, run one `tower-crane wait --for orchestrator --after <cursor> --timeout <deadline-seconds>` as a background command through your harness (Claude Code background Bash or Monitor, Codex background execution, or the equivalent). Use the startup snapshot's offset or your last handled event's `id` or byte `offset`. Keep one outstanding wait for the shared stream. If it is already running, keep it when you dispatch another agent. Its completion delivers one JSON event. Save its cursor, handle it, then arm the next wait with that cursor so events during dispatch or handling are retained. Your own writes are skipped unless your identity is `owner`; owner input and engine exit and stall observations still wake you.
- **Leases.** Read `limits.lease_minutes` with `tower-crane project show`; size `MIN` to cover expected work and waits. Workers renew their own leases as they report progress. A `stall` event means the lease and progress are stale; inspect the task and worker log once before recovery. For `worker-exited`, read the task once: if it still has a claim, run `tower-crane release ID --reason "<exit diagnostics>"` under your own identity. The engine allows this only when it verifies the current spawned process exited. A worker that failed before claiming needs no release. Then dispatch a replacement. Never re-dispatch a task while its worker is alive.
- **Gate submitted work.** Read the task's kind with `tower-crane task show ID`. `tower-crane accept ID --cmd "<scoped test command>"` runs missing tests, clean, sources and CI gates before review: tests and clean for code, sources for research kind on every tier, CI for every task with a PR. Research requires network evidence from at least `research.min_sources` distinct pages (default 10); the sources gate fetches each citation and checks the quotes in committed `research/ID.json`. Verify other kinds as their briefs require. A confirmed failing gate is a `tower-crane rework ID --reason "<gate summary>"`. An unfinished CI is not a rework reason. Dispatch a gate runner with a unique identity different from yours, such as `gate-ID-N`, to watch `gh pr checks <pr> --watch` with a deadline. When CI completes, it re-runs `tower-crane check ci ID --agent <gate-name>` once, then sends `tower-crane msg --to orchestrator --task ID --agent <gate-name> "<result>"`. Pass the absolute state path with `--state <dir>` when its state environment is absent. Both writes wake your wait because the runner records its own identity. Act on that event: fix an observation or configuration failure, send a confirmed CI failure to rework, or accept again after a pass.
- **Review.** After the software gates pass, `accept` dispatches a clean-context reviewer following `tower-crane-review`. `review_pending` leaves the task submitted; handle its review evidence event, then accept again. Failed or invalid attempted gates need an explicit check rerun. `tower-crane spawn --role review --task ID` uses the same guarded choice; use `--dry-run --json` to inspect the selected route without starting it. The reviewer receives the diff, acceptance and gate results and uses those results unless making a focused probe. CI is the orchestrator's gate; reviewers judge code and acceptance. For a native reviewer on another harness, use the selected model and pass those same inputs with a unique name different from the submitter, absolute worktree and state paths and skill path. Review policy, including prices and risk globs, is operational: change it yourself with `project set --review-policy JSON` when the run needs it, and record why in a task note. Native agents pass `--agent <name>` on every tower-crane call and `--state <dir>` when the state environment is absent.
- **Merge.** With review ok, `tower-crane accept ID` must pass, then `tower-crane merge ID` for a PR. CI must be green at the submitted head for every PR, regardless of kind. If CI evidence needs refreshing, run `tower-crane check ci ID` and use the gate runner above while it is unfinished. Fix any refusal's cause.
- **Rework.** Review or CI findings go back with `tower-crane rework ID --reason "<findings>"` and the brief updated with what the next attempt must change. When the same area fails review twice, stop patching it: send it back with a simpler design, removing the mechanism if the task can live without it. Each patch on a fragile design opens the next finding.
- **Carry results forward.** After an accept, update the briefs of tasks that depend on it with what they now need to know (an interface, a decision, a path). Keep them short.
- **Stacks.** A submitted dependency can unblock a single chain before it merges. Prepare its upper worktree normally; the CLI verifies the lower head and uses its branch as the PR base. Spawn supervisors link submitted PRs automatically; for native workers, run `tower-crane stack link ID` after submission. Accept every lower task before merging an upper one. The merge gate rechecks all heads and uses GitHub's atomic stack merge. After a lower merge or main moves, idle stacks refresh through `tower-crane stack sync`; changed heads and conflicts require rework. Handle deferred sync events after the live worker exits. If stacks are unavailable, use the ordinary accepted-dependency flow. For a repository requiring admin merges, use the owner's `merge.admin` policy, run `tower-crane stack unstack ID`, then merge lower tasks individually. See docs/cli.md for the same-repository and auto-merge limits.
- **Decisions and messages.** Handle `worker-message`, `owner-comment`, `decision-opened`, `decision-answer`, `owner-done` and `released` events when the wait completes. Read the affected task or decision once and update its brief when needed. Other changes also wake you; use their command and task to update the plan once. When something needs the owner, `tower-crane ask --question ... --option ... --recommend ... --why ... --blocks ID` and keep the rest moving. Record an answer the owner gives in chat with `tower-crane answer`.
- **Native usage.** On each native worker or reviewer completion, record its reported usage once: `tower-crane spend ID --tokens N --input I --cached C --output O --rung R --harness H --model M --agent <native-name>`. Omit unavailable components; input includes cached tokens. Pass the rung, harness and model used for that dispatch even if the ladder changed. Native Agent-tool usage cannot be recovered from a spawned CLI log. If the tool gives no counters, record that limitation with `tower-crane task note`. Spawned CLI agents are counted automatically on exit; do not add their tokens again.
- **Spend.** Read `tower-crane status` when an event changes the plan. A task that runs past twice its size gets split or re-planned. Record minutes with `tower-crane spend`. Status shows spawns without usage; retry `tower-crane spend ID --from-spawn <spawn-name>` when captured telemetry is available.
- **Deadlines.** `wait --timeout` exits 2 with `{"type":"timeout","offset":N}`. Save that cursor before handling the deadline. Choose the deadline from a real task, lease or owner deadline. A timeout is a deadline to handle, not a reason to repeatedly query status. Omit `--timeout` when there is no deadline. The CLI owns filesystem watching and process detection; the agent waits for command completion.

## 4. Report

When work stops: what was merged (PR links), what is waiting on the owner (decisions and `needs_owner` tasks), spend against budget, and the sketch path. Short.

## Rules that keep this cheap and honest

- Software first: a gate or a CLI query answers before any model reads anything.
- You do not write the change yourself, apart from fixing the plan. If you are tempted to, make it a task.
- Evidence is recorded at the submitted commit; a new commit needs new evidence.
- A refused accept or merge is information. Read why.
