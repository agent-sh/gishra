- Opencode spawns render primary role agents in a private config and HOME with isolated XDG directories and linked credentials. Native tool, skill, web, Git, gh and path permissions follow the role; rung tool and MCP opt-ins appear in dry-run. Provider and MCP config layers merge nested fields recursively, with arrays replaced. Native tool names and agent-file aliases receive the same authority classification. House-rule receipts use original user config paths and mark files to read. A three-run stub measurement records the startup context reduction in docs/ladder.md. The stub fixture preserves inherited Path casing on Windows.
- Harness capabilities are declared once in lib/agents.js. Authority and its tests require OS command confinement for operational primary, fallback and default-harness moves. Opencode has both sandbox capabilities false: its native file-tool rules cannot prevent shell writes, so moving a confined role to it requires the owner.

- OpenCode excludes wellknown credentials from its native auth input so remote configuration cannot restore instructions, plugins or MCP servers. API/OAuth values reach only the agent process; the credential source stays linked and auth writes stay private. MCP authority checks include inline OPENCODE_CONFIG_CONTENT, matching spawn. A local HTTP probe covers the remote discovery exclusion.

- Opencode provider copies follow the same allowlist as codex: named, type-checked package, connection and model metadata fields only, so a credential under any key name stays out of the home.

- The OpenCode stub rejects prototype-mutating keys at every config depth. Its credential isolation test compares and reads open file descriptors, with cleanup on failure, instead of checking a path before reading it.
